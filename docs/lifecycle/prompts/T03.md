## Rules
- `proposals.donor_id` NOT NULL from creation. A co-funder = a separate proposal (D-24). A project may have any number of proposals; add no "one proposal per project" constraint.
- `requested_budget` is optional now (T04 requires it from `proposal review`). It's money: never add it to an existing select, the CSV export, a notification payload or `activities.changes`.
- `target_beneficiaries` is nullable (T04 requires it from `proposal review`). Do not touch `projects.target_beneficiaries`. `projects.working_days` is the only `projects` change in this task.
- Funded = donor approval (D-28): nothing here marks a proposal funded at `submitted`.

## Data integrity (migration order: MySQL does not roll back DDL)
1. **Pre-checks before any DDL**: duplicates in `donor_proposal`, and proposals without an agreement → `RuntimeException` listing the ids (Finance names the donor, then re-run).
2. Add the columns (`donor_id` nullable, no FK) → backfill inside `DB::transaction` with `lazyById` → assert no NULL → `donor_id` NOT NULL → FK `restrictOnDelete` → unique `proposals(id, donor_id)`.
3. Migration 2: repeat the duplicate pre-check, check no agreement donor differs from its proposal's, then unique `donor_proposal.proposal_id` and the composite FK `ON DELETE RESTRICT ON UPDATE RESTRICT` (never CASCADE). Keep the existing single-column FKs.
4. Explicit index/FK names. `down()` reverses in order. Ask before running `migrate:rollback --step=…` locally.
