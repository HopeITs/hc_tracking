## Rules
- **Create** only when `proposal.status->isApprovedByDonor()` and no agreement exists. `donor_id = proposal.donor_id`, always written by the server; a forged `agreementDonorId`/`donor_id` is ignored. **Update** never changes `donor_id` or `proposal_id`. Editing a legacy agreement on a non-approved proposal stays possible and shows «حالة المقترح لا تتسق مع وجود اتفاقية» / "The proposal status is not consistent with having an agreement" (replaces the old "not approved" warning).
- **Self-funded** (`donor->is_internal`): the agreement is optional; no transfers are ever generated.
- **Budget** defaults to `requested_budget` (editable); **currency** defaults to `requested_currency` and locks once transfers exist (existing rule). Delete rules are unchanged.
- **Installments** (`SaveAgreementInstallments`): PR Manager and Finance (`funding-agreements.update`). Sequence 1…n, amount > 0, currency = the agreement currency, `scheduled_date`. At least one installment; each `scheduled_date` inside the agreement term. A sum ≠ budget → a warning the user must confirm explicitly (not a block). Editing the schedule after generation adds a transfer row for a new installment only. Removing an installment whose transfer has no actual data deletes its generated row; with any actual data (transfer/arrival/receive date or received amount) the removal is refused. Existing agreements with manual transfers get no schedule and no generation (D-31, T27); manual rows are never touched or duplicated.
- **Generation** (`GenerateExpectedTransfers`, queued, idempotent per `installment_id`): runs after `FundingAgreementRecorded` and after each `SaveAgreementInstallments` commit. For each installment without a transfer it creates one `transfers_tracking` row: `source = auto`, `installment_id`, `payment_amount` = installment amount, currency, `scheduled_date`; `transfer_date`, `arrival_date`, `receive_date`, received amount, `fees`/`fees_currency` (commission) and exchange rate stay empty for Finance. It never generates for a non-donor-approved or self-funded proposal. It locks the agreement row (`lockForUpdate`) before checking, so two workers can't both insert. No money is computed inline: `AgreementMoney` / `TransfersTracking::stateSql()` only.
- **Four dates** on transfers (D-31a): `scheduled_date`, `transfer_date`, `arrival_date` (bank / transfer company), `receive_date` (organisation account). Order transfer ≤ arrival ≤ receive, with hints under the fields. Update `TransfersTracking::stateSql()` and `Tranches::timing()` **together** (the single state definitions, `support-models.md`) so "in transit" lasts until arrival, and add the PHP/SQL parity test the rule file asks for.
- **Authorization:** `funding-agreements.create/update` in the action (`Gate::authorize`) and in the trait before any work. The submitted proposal id is re-validated: exists, donor-approved, no agreement, inside the page scope (`agreementProposalScope()`/`agreementDonorScope()`). The generator runs as the system: it takes ids from the event or job, re-reads the rows, and records Activity with the system actor; document its exemption in `ActionAuthorizationTest` with a test.
- **Concurrency:** the save runs in one transaction and loads the proposal with `lockForUpdate` before the pre-check, so the check and the insert see the same row; the unique index + composite FK (T03) stay the guarantee. Generation runs in its own transaction after the agreement's commit; each generated row's amounts come from its installment as stored, never recomputed. An agreement recorded before or after template confirmation produces the same rows.
- A proposal corrected away from `approved` (**Correct Status**) after the agreement exists keeps the agreement; both pages show the inconsistency warning. A co-funder is a separate proposal (D-24), never a second agreement.
- **Money:** the pre-fill reads `requested_budget` only for users allowed to record agreements. `proposalOptions()` selects `id, name, internal_project_number, status, donor_id` + a narrow donor eager load; no money columns. `transfer.generated` (to Finance and General Management) carries no amount for non-finance recipients.
