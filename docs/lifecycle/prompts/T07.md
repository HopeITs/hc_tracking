# T07 · Review loop for concept note and proposal · Dev 2 · days 7–9 (merged by CP3)

## Goal
When a proposal enters `concept note review` or `proposal review`, the default reviewers and the people involved become reviewers and are notified (with the meeting time if set). Each can **Mark as Seen** with a note. `proposals.manage-reviewers` holders add or remove extra reviewers. MEAL attaches a **Need Assessment**. Sending to the donor warns about unseen reviewers but never blocks.

## Rules
- Review rows are per stage; `concept_note` rows never count for `proposal`.
- `InviteDefaultReviewers` is idempotent. **First entry** into a stage adds:
  - the four default slots (resolved now through `Slots::holderOf`; a vacant slot → "Position vacant" / «المنصب شاغر» warning, no row, the transition still succeeds);
  - every linked project's owner (`projects.user_id`) and program manager (`programs.manager_id`).

  **Re-entry** after a send-back: never remove or re-slot rows; add only owners/program managers of newly linked projects; re-notify only `seen_at IS NULL`. Settings or holder changes are never retroactive.
- Same person in two slots → one row with the highest-priority slot (enum order).
- **Mark as Seen** sets `seen_at` once (a second click changes nothing). The note is editable only while the status equals the stage's review status.
- **Remove:** only slot `additional`, only while `seen_at IS NULL` and `note IS NULL`. **Add:** the stage is derived server-side (`concept note`/`concept note review` → concept_note; `proposal draft`/`proposal review` → proposal); other statuses refuse.
- Reviewers without a login show the existing "no account" warning (`assignedEmployeeIds()`).
- **Authorization:**
  - Add/remove: `manageReviewers` → `proposals.manage-reviewers`.
  - Mark/note: only the row's own person (`employee_id === auth()->user()->employee_id`; null never matches), with the row loaded via `$proposal->reviewers()->whereKey($id)->firstOrFail()`.
  - `view`: `proposals.view` OR a reviewer row for the user. **Never grant `proposals.view` to reviewers.** Reviewers without money permissions see no money: verify `canViewAgreements()`, `canViewTransfers()`, `hiddenCollections()`, `requested_budget` are skipped for them.
  - `uploadNeedAssessment`: `proposals.update` OR (a reviewer on this proposal AND `results.create`), through `SaveProposalFile` or a sibling action.
  - `ProposalRecipients::permissionExemptUserIds()` returns the reviewers' user ids for these events. Verify `OpenNotificationController`/`SubjectLinks` let a reviewer open the link.
- Audit: every add/remove/mark/note edit is an activity on the proposal. Notifications are queued after commit and carry no amounts.

Validation (`lang/{en,ar}/proposals.php`, admin section in `notifications.php`):
- `employeeId`: required, integer, exists in HR, not already on (proposal, stage) — "This person is already a reviewer for this stage." / «هذا الشخص مضاف بالفعل».
- `note`: nullable, max:2000.
- `meetingAt`: nullable, date, after:now.
- Need assessment: the existing proposal-file rules (`SecureUpload`, 5 MB, pdf/docx/xlsx/jpg/png).
- Settings: each slot is a nullable HR position id.

Concurrency: double Mark → `seen_at` unchanged, no second activity. Two managers add the same person → unique index; catch the `UniqueConstraintViolationException` narrowed to the index name → "already added". The proposal leaves the stage mid-edit → the action re-reads the status and refuses. An inactive HR employee: the row stays, shown as «حساب غير فعّال», never notified.
