# T23 · Who supervises whom: HR source, exceptions, escalation, My Team · B3 · days 2–3 (CP3) · 3 slices

## Goal
Supervision is a **routing fact, never a permission**. The supervisor of an employee is the **HR direct manager** of their current position (`EmployeeProfile::managerOf()`, contracts §10, D-13). A local `supervisions` table holds **exceptions and additions only** (an extra supervisor, or an override where HR is wrong or missing); it never duplicates HR. Three uses:
1. overdue escalation also reaches the supervisor, next to the program manager;
2. a read helper `SupervisionMap` (T17 "prepare on behalf", T21 recipients);
3. a **My Team** card on Home showing each supervisor what their people have outstanding.

A **Supervision** tab in Users & Roles (`/admin/users`) lets General Manager maintain the exceptions and shows the HR relations read-only.
- **Slice 1 (day 2):** table, model, `SupervisionMap`, actions, policy, tests.
- **Slice 2 (day 3 am):** Supervision tab, escalation, catalog keys.
- **Slice 3 (day 3 pm, last; cut list item):** My Team card. Drop it first if late; nothing else depends on it.

## Rules
- **Table:** `id`, `supervisor_employee_id`, `supervisee_employee_id` (unsigned big int, HR ids, **no FK**), `created_by` FK `users` null `nullOnDelete`, timestamps; **stored generated columns** `pair_low`/`pair_high` (`LEAST`/`GREATEST` of the two ids) with unique `supervisions_pair_unique` (blocks a duplicate **and** a direct A↔B loop in the database, even for two admins acting at once); index `supervisions_supervisee_idx`. Model: `#[Fillable]` the three real columns only, `casts()`, `TracksActivity` + `RecordsActivity`, `activityEmployeeFields()` both columns, morph key `supervision`, `activityModule()` = `access-management` (reuses `UserRecipients`; no new module icon or banner), `SubjectLinks::routeFor('supervision')` → `admin.users.index` with `tab=supervision`. Working `down()`.
- **`SupervisionMap`** (`App\Support`; signatures in `contracts.md §10`): merges `EmployeeProfile::managerOf()` with local rows; active HR employees only; de-duplicated; memoized per request (one HR query for the active flags, never per-row). Resolve HR ids first, never `whereHas()` across connections. It reads no `contracts` column beyond what `EmployeeProfile` exposes.
- **Business rules (add/remove):**
  - nobody supervises themselves; a person may have several supervisors; chains longer than 2 are allowed;
  - both employees must be **active in HR** at creation (re-checked server-side; the picker list is never trusted);
  - a local row that repeats the HR direct manager is refused;
  - an employee who later goes inactive keeps the row (shown "Inactive" with an icon, not colour alone) but has no effect in the helper, the card or escalation;
  - removing takes effect immediately; removing an already removed row is a no-op with a message.
- **Escalation:** in the program-manager branch of `EscalationScanner` (`escalate_manager_after_days` within `escalation_catch_up_days`, both from `NotificationSettings`, never hard-coded), the active supervisors of the people in `DeadlineItem::directUserIds` (mapped user → employee id) also get a Critical alert, key `notifications.alerts.escalation.supervisor`, stage `supervisor:{due}`.
  - Skip anyone already notified as program manager for that item and the named person themselves.
  - "Named people" = exactly `directUserIds` as `DeadlineCatalog` builds them (assignees plus the task creator): the same set the manager stage already uses. Items watched only by roles get no supervisor escalation.
  - For tasks keep only supervisors for whom `TaskVisibilityScope::allows($user, $task)` is true, so a title never reaches someone who cannot open it; other modules go through `RecipientFilter` via `AlertDispatcher::send()`.
  - Load the map and HR active flags **once per scan**; user ↔ employee ids in one query; no per-item queries.
- **My Team card** (slice 3): shown only to a user with a linked employee who supervises ≥ 1 active employee. Sections: overdue open tasks of supervisees (count per person + link); unsent monthly reports (only if T17 is merged); donor reports due for supervisees (only if T19 is merged and the viewer holds `funding-agreements.view`; no amounts). Unbuilt sections are follow-ups, never placeholders. One `myTeam()` computed with a fixed query count (supervisee ids, HR names, tasks grouped by assignee, one per optional section); when the user supervises nobody, only the first query runs. The task query runs **as the signed-in user** so `TaskVisibilityScope` applies. Add `data-my-team` and `data-my-team-person` as stable `data-<name>` tour hooks (see `config/tour.php`) (T26).
- **Authorization:** `supervisions.manage` → `Gate::authorize` inside each Action and at the top of each Livewire method; the tab button is hidden and its methods 403 without it. The route keeps `viewAny` (`access-management.manage-users`); General Manager holds both. Do not widen the route; report it if some role gets `supervisions.manage` alone. `created_by` = `auth()->id()`; component ids are `#[Locked]`. One `SupervisionPolicy` (or list the model in `PolicyCoverageTest::modelsGuardedWithoutPolicy()` with module `supervisions`, as Dev 1 prefers).
- **Concurrency:** add/remove in one `DB::transaction` through Eloquent so `RecordsActivity` fires. A double submit or the reverse pair from another admin hits the unique index: catch `UniqueConstraintViolationException`, re-read to decide which message applies, never a 500.
- **Events:** `supervision.added` / `supervision.removed` (digest, MEAL + General Management) registered in T21's `EventCatalog` (`EventCatalogCoverageTest` stays green). If the catalog is not merged, add the keys in your PR and tell Dev 1.
- Flux modals bound with `wire:model`; `x-ui.*` components; logical Tailwind classes; list grouped by supervisor with a "From HR" label on HR relations, search, add modal with two `x-ui.form-select` employee pickers, a remove confirmation; no `@php(...)`.
