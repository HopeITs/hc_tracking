# T08 · Proposal approval, project approval and the ActivateProject entry point · Dev 1 · days 9–10

## Goal
1. **Approve Proposal:** one atomic action moves a proposal from `submitted` (or `on hold` entered from `submitted`) to `approved`. It fixes the grant dates, gives every linked project those dates, and moves each project whose owner has acknowledged to **`approved`**. Projects whose owner hasn't acknowledged wait (dated draft + badge) and move to `approved` the moment the owner acknowledges.
2. **ActivateProject:** the single Team A entry point for `approved → active`. T33's `ConfirmReportTemplate` calls it; it dispatches `ProjectActivated`.

Approval is **not** activation (D-04b, D-39). A project becomes `active` only when MEAL confirms its template.

## Rules
**ApproveProposal**
- Source must be `submitted`, or `on hold` whose pre-hold status is `submitted`. Otherwise it's refused with no write («المقترح معتمد بالفعل» when already approved, else T04's `transition_not_allowed`).
- Required:
  - `actual_date_begin`, defaulting to `planned_date_begin`; if the decision is later, the approval date or a later date with a note (D-04);
  - `actual_date_end` ≥ begin;
  - `decision_date` ≤ today;
  - donor-approval evidence: a `media` file in category `donor_approval` **or** `approval_note` (min 10) (D-26).
- At least one linked project, else «اربط مشروعًا أولًا».
- The proposal gets `approved`, both actual dates, one `ProposalStatusNote` (effective = decision date, `changed_by`), and `ProposalStatusChanged` after commit.
- No agreement is required. "No agreement recorded yet" / «لا اتفاقية مسجلة بعد» shows on the project page until one exists (`TransitionResult`/`ApprovalResult` warning `no_agreement`).
- `ProposalPolicy::approve` → `proposals.update`, authorized on the **reloaded** row.

**Per linked project** (read from `$proposal->projects()` inside the transaction, locked in ascending `projects.id`), via `ApproveProjectFromProposal($project, 'proposal_approval')`:

| Project state | Effect |
|---|---|
| draft, owner acknowledged (or self-assigned) | dates = earliest begin / latest end of its donor-approved proposals → **`approved`** |
| draft, owner not acknowledged | gets the dates, stays `draft` with the badge «بانتظار تأكيد المالك» / "Awaiting owner acknowledgement" |
| owner-rejected (`isOwnerRejected()`) | unchanged; top level notified (existing ASG behaviour) |
| `approved` | dates extended (never shortened) |
| `active` (renewal / second proposal) | dates extended, never shortened; `ProjectPeriodChanged` after commit; owner notified when the end moves |
| `archived`, or `closed` after linking | skipped and named in the result |

**Owner acknowledgement hook:** when an `Assignment` on a `Project` for field `user_id` is acknowledged (page `submitAssignment`, `QuickActions::runAssignment`, self-assignment via `syncAssignment`, and re-ask after `unblock()`), call `ApproveProjectFromProposal($project, 'owner_acknowledgement')` **in the same transaction**. It's a no-op unless the project is a draft with a donor-approved proposal. Idempotent; both paths lock the project row.

**ActivateProject** (`contracts.md §6`)
- Preconditions: project `approved`, both dates set, owner acknowledged. Otherwise it refuses with no write.
- Sets `active`. Each linked proposal that is `approved` (donor-approved, not yet active) → `active` with one status note ("Activated with the project's report template"). Dispatches `ProposalStatusChanged` per proposal and `ProjectActivated(projectId, proposalId = the earliest such proposal or null, start, end, via)` after commit.
- `Gate::authorize('activate', $project)` → `ProjectPolicy::activate` = `report-templates.manage` (MEAL). The caller (T33) also authorizes.
- `$via` ∈ {`template_confirmation`}; anything else → `InvalidArgumentException`.

**Authorization of automatic paths:** `ActionAuthorizationTest` requires `Gate::authorize(` in every `app/Actions/Projects` file. `ApproveProjectFromProposal` authorizes `approve` on the proposal for the approval path and `respond` on the assignment for the acknowledgement path. Never weaken the test silently.

**Notifications** (after commit, queued, no amounts): Finance ("Record agreement needed", linking to the proposal), each project owner, program manager, MEAL Manager (`Slots::holderOf('meal_manager')`), PR Manager, and the proposal's reviewers (if T07 is merged; otherwise behind one clearly named method + follow-up). Activity events (catalog keys, `contracts.md §15.2`): `proposal.approved`, `proposal.approved_without_agreement` (D-26 warning), `project.approved` (via, proposal id), `project.owner_acknowledged`, `project.owner_declined`, `project.period_changed`, `project.activated`. Override `activityEventForChange()` so there's one event per change; update `ProposalRecipients::isKeyEvent()` for `proposal.approved` and `ProjectRecipients` for `project.approved` (projects reach `approved` again).

**UI**
- **Approve Proposal** modal on `proposals/⚡show` (`wire:model="showApproveModal"`, `#[Locked]` ids): actual begin/end, decision date, evidence (file upload or note), and a preview of linked projects (will be approved / will wait for owner / skipped).
- The Change Status modal points to it instead of offering `approved`.
- Badges on `projects/⚡show` and `⚡index`: "Awaiting owner acknowledgement", "Awaiting funding" («بانتظار التمويل», proposal `submitted`), "Awaiting MEAL template" (project `approved`).
- The result message lists approved, waiting and skipped projects.
