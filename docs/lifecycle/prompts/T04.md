## Rules (beyond §1/§2)
- `TransitionProposal` refuses `→ approved` (ApproveProposal, T08), `approved → active` (ActivateProject, T08) and any terminal source (CorrectProposalStatus). A target the client was never offered → validation error; hiding options is not protection.
- `CorrectProposalStatus`: source must be `rejected` or `completed`; target any live status except `approved`; mandatory reason; note `is_correction = true`; ability `ProposalPolicy::correctStatus` → `proposals.correct-status`.
- `RecordFinalReportAcceptance`: `proposals.update`; sets `final_report_accepted_on` (≤ today) and `_by` = actor; requires the `final_report` media file to exist; records activity `proposal.final_report_accepted` (`contracts.md §15.2`).
- `final_report` requirement reads `milestones` where `proposal_id` = the proposal and `is_final_report` = true and status is complete, plus the media and acceptance columns. Self-funded (`donor->is_internal`) skips acceptance.
- `on hold` targets depend on the pre-hold status (§2). `stage()` for on hold / rejected = the stage of the pre-hold / pre-rejection status.
- Transitions need `proposals.update` via `ProposalPolicy::transition($user, $proposal, $to)`, checked inside the action on the row reloaded with `lockForUpdate()`. Stale `expectedFrom` → stale message, no write.
- Remove `status` from `Proposal`'s `#[Fillable]` (grep for `fill([` / `create([` / `update([` callers with `'status'` first).
- Phase is derived. `match` arms are exhaustive, no `default` (the enum badge's existing `default` is the one exception; add explicit tones anyway).
- Activity: status changes still raise `proposal.status_changed` through `Proposal::activityEvents()`; notes carry no money.
- Gantt progress (slice 2): CN 5 · CN review 8 · CN submitted 10 · proposal draft 15 · proposal review 22 · submitted 30 · on hold 30 · approved 45 · active 65 · completed 100 · rejected (existing tone).
- Scanners: `DeadlineCatalog`/`StalledScanner` skip `on hold` too (its reminder comes in T21).
