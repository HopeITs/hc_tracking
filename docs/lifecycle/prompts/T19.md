# T19 · Dynamic donor reports · Dev 2 (Team A) · days 10–12 · 2 slices

## Goal
The Projects & Fundraising Manager picks a proposal and a period (quarterly, semi-annual, annual or custom). The system aggregates the **validated** monthly report figures of that proposal's centers into one read-only report, which can be saved as a versioned snapshot, exported and delivered to the donor.
- **Donor Report Builder** (`/donor-reports/compose`): per indicator target, period total, cumulative to period end, achievement %, broken down per center; disaggregation (D-50); activities (D-51); narratives per center per month; links to monthly report files; a completeness warning; a finance section **only for `funding-agreements.view` holders**.
- **Save** freezes a snapshot; **Regenerate** creates version + 1; a submitted report never changes.
- **My Reporting Duties** lists a person's reports with no money. Reminders go to the responsible person.
- CSV export and a print view (browser PDF). No `report_schedules`, no schedule generator, no Extend/Stop (D-32).
- **Slice 1 (day 10):** enums, migration, `DonorReportAggregator`, period math, `ComposeDonorReport`, `SaveDonorReportSnapshot`, `RegenerateDonorReport`, policy. No UI.
- **Slice 2 (days 11–12):** builder and snapshot pages, submission and files, duties page, reminders, export/print, Funding Agreement list.

## Rules
**Aggregation (`DonorReportAggregator::aggregate(Proposal, CarbonImmutable $start, CarbonImmutable $end, bool $includeFinance): array`)**
- Read-only, constant query count (10 centers × 12 months). The array is the snapshot payload (`schema_version` 1): period, header, indicator rows, per-center breakdown, disaggregation, activities, narratives, files, completeness, finance.
- **Donor view only (§14.1):** figures come from that proposal's targets' **share mirrors** (`reports.monthly_report_id` set, `status = approved`), so `split` already holds each donor's share and no split logic lives here. The footnote "shared with another funding" appears for `shared` items only. A center linked mid-period appears from its first generated monthly report (no pivot needed).
- Counts sum. `is_cumulative` → latest validated value, never a sum. Percentage and average = `PlanIndicator::pooledRatioSql()`/`pooledRatio()` across the proposal's centers, with a per-center breakdown; fixed-denominator indicators = Σ center counts ÷ Σ their `project_proposal.target_beneficiaries`, showing each center's beneficiaries. Lines without a denominator are listed in the completeness section. The snapshot stores numerator and denominator, not only the percentage (and the denominator used).
- Tracking-only indicators (`indicators.is_tracking_only`) show the value without achievement %. Indicators removed from the framework after reports exist go in a "historical indicators" section with their recorded values.
- **Disaggregation (D-50):** per center and for the proposal, male, of whom PwD, female, of whom PwD, total, from share-level `monthly_report_line_breakdowns` (validated only), stored as numerators and denominators; fixed-denominator indicators show counts only.
- **Activities (D-51):** each activity's status at period end (latest validated `monthly_report_activity_entries` on or before the end) and its execution months.
- **Narratives:** `monthly_report_answers` of validated reports (question text at answer time + answer), per center per month. File **links** to the monthly report files, never copies (media ids and owners).
- **Header** from system data: donor contract number (agreement external number), implementer, project title, goal.
- **Completeness:** per center and month in the period that has a `monthly_reports` row: `draft` → not submitted, `submitted` → not validated. A clear warning at the top; both are never counted. A period with no validated data shows «لا بيانات متحقق منها في هذه الفترة» / "No validated data in this period." and can still be saved.
- **Finance** (only when `$includeFinance`): transfers of the proposal's agreement with `receive_date` in range, one line per currency, amount received, `fees` (+ `fees_currency`), net, through `AgreementMoney` / `TransfersTracking::stateSql()`. No local money formulas. For non-holders skip the query server-side and write no finance key into the snapshot.

**Periods:** inside the grant (`actual_date_begin`…`actual_date_end`): quarterly = 3 months from the start month, semi-annual = 6, annual = 12, clipped at the grant end; custom = `startMonth`…`endMonth`. Calendar months via `addMonthsNoOverflow`. A period outside the grant is refused for new compositions; existing snapshots stay when the grant changes.

**Who and what**
- Eligible proposals: approved by the donor (`isApprovedByDonor()`: approved, active, completed), visible to the user, and **not** a self-funded proposal (internal donor, D-27a): refused with the message below. `ReportAudience` stays (`donor` | `internal`) for who reads the report.
- Compose and save: `reports.aggregate` **and** `view` on the proposal, via `Gate::authorize` inside every action. Public Livewire writes authorize themselves (`AuthorizationCoverageTest`); view helpers stay `protected` (`BrowserCallableMethodsTest`). Re-load the proposal id on the server (approved and visible).
- **Save without an agreement:** `donor_reports.donor_proposal_id` is NOT NULL, so the builder previews but disables **Save** with a message.
- **Snapshot:** stores `schema_version`, `generated_at`, `generated_by`, proposal/donor/center names, period, rows, breakdowns, narratives, file references, completeness, and the finance section only if the generator held `funding-agreements.view`. A saved report never changes when monthly data changes later; the builder shows the difference only on regenerate.
- **Versions:** Regenerate on an unsubmitted report inserts a new row with `version + 1` (same agreement, type, period). Compute `max + 1` while locking the agreement row; the unique index (§14.2) is the backstop (retry once). Concurrent generation yields two visible versions. A submitted report is never regenerated or edited.
- **Due date:** `due_on` is required (column stays NOT NULL), entered per report. Reminders before and after it in working days, thresholds from `NotificationSettings`.
- **Default responsible:** narrative → `Slots::holderOf('fundraising_manager')`, financial → `Slots::holderOf('finance_manager')`; editable; no new slot. Inactive in HR or without a login: the slot holder becomes direct, both pages show a warning.
- **Submission** (**Mark as Submitted**): transaction + `lockForUpdate`, re-check `submitted_on IS NULL`; `submitted_on` ≤ today; `audience = donor` needs ≥ 1 `report_submission` file (D-21), `internal` may have none; a second submit gets the "already submitted" message and writes nothing. A partial failure deletes written files (`StoredFiles::forget`).
- **Policy:** `DonorReportPolicy` exactly as `§14.3` (responsible = `responsible_employee_id` equals `$user->employee_id`, both non-null). Saved reports load through the policy; files through `$donorReport->media()->whereKey($mediaId)->firstOrFail()` (BOLA).
- **My Reporting Duties:** title, type, audience, period, version, due/submitted dates, donor name and proposal name as plain text. No amounts, currencies, agreement files, or links to `funding-agreements.show` / `proposals.show` / `donors.show` without that page's permission. Never grant `funding-agreements.view` to responsibles as a shortcut.
- **Export and print** use the saved snapshot (no live re-query), the same permission, rate limited. The finance block renders only for `funding-agreements.view` holders, in the page, the export and the print. Notifications carry no amounts.
- **Events** after commit: `donor_report.saved`, `donor_report.submitted`. Activity Log: save, regenerate, submit, file add/remove. The print view is a plain Blade layout for browser print-to-PDF.
