> **Out of the October window; don't start before Dev 1 says so.** D-18 postponed the annual-plan workflow to early 2027. D-44a makes it mandatory from January 2027: every program manager must enter their annual plan, so ship it before then (November plan). Nothing else depends on it.

## Goal
An annual plan gets a status (`draft` → `approved`, with approver and date). The program or branch manager lists the **activities** the plan will deliver, picked from the program's own framework (`results.type = 'activity'`), with planned months, like the Gantt template's "Planned / Implemented" rows. MEAL enters the targets as today (D-23). "Implemented" months are **derived** from the milestones linked to each activity, never typed. The **Annual Plan** page then answers "which indicators and activities must be achieved, and which milestones reached", in a draft or approved state. Every existing plan becomes `approved` so **Executive Summary** numbers do not move.
- **Slice 1:** schema, enum, models, policy, three actions, guards on other pages.
- **Slice 2:** Annual Plan tabs and grid, matrix draft marker, Executive Summary marker, lang.

## Rules
- **Status:** new plans start `draft` (`AnnualPlan::$attributes`); the migration marks every pre-existing plan `approved`, `approved_by` NULL, `approved_at` NULL; the UI shows "Approved (before workflow)".
- **Editing:** draft: targets (MEAL, `targets.*`) and activities (`annual-plans.update`, plan manager or program manager) are editable. Approved: read-only; a change first needs **Return to Draft** with a reason (>= 10 chars) recorded in the Activity Log with the actor (`ReturnAnnualPlanToDraft`, gated by `update`).
- **Activity source:** `results.type = 'activity'`, `results.program_id = annual_plans.program_id`, `results.proposal_id IS NULL`. Nothing else is accepted.
- **`planned_months`:** distinct integers 1-12, stored sorted, at least one. Unique (`annual_plan_id`, `result_id`).
- **Implemented months (derived):** a month of the plan year is implemented when a non-cancelled milestone with `milestones.result_id` = the activity, in a project of the plan's program, has an actual period (`actual_start_date` to `actual_end_date`, or today when open) overlapping it. Read for the whole tab in one query. Milestones linked to proposal-framework activities are not counted in v1; say so in the handoff.
- **Approve:** only from `draft`; the approver must not be `prepared_by` (the user who last saved the activities); sets `approved_by`, `approved_at`. A plan with no activities or no targets can be approved, with a warning. Any `annual-plans.update` holder who is not the preparer may approve. **Super Admin is never the intended approver and never the only test account (D-20a)**: tests use General Manager, Managers and MEAL accounts.
- **Executive Summary:** all plans count as today; draft plans are marked ("N drafts" on the coverage card, added to the existing `plansOf()` select and a conditional aggregate, never a new query). A migrated plan keeps every number unchanged. Count drafts the same way in every card.
- **Guards elsewhere:** `targets/⚡index` refuses writing an annual-plan target while the plan is `approved`; `results/⚡index` refuses deleting an activity linked to a plan, and refuses a type change or program move that strands a plan activity (page guard in `canDelete()` plus `ResultObserver`; the `restrictOnDelete` FK is the backstop); `savePlan()` refuses reassigning a plan to another program while it has activities.
- **Cascade:** deleting a plan cascades its activities; `PlanIndicatorSourceObserver` still deletes its targets. Verify `ProgramObserver` removes plans (and their activities) before results so the restrict FK never fires.
- **T33 interplay:** plans from `annual-plans:ensure-2026` that exist when this migration runs become `approved` by the backfill; MEAL must **Return to Draft** to edit their org-wide targets. If the command can run again after this task ships, it must create `approved` plans: that edits a T33 file, so escalate to Dev 1.
- Plans without activities keep T16's fallback chain view; plans with activities show their own list.
- **Concurrency:** both Actions lock the plan row (`lockForUpdate`) first, then its activities (fixed order). Approve expects `draft`, so a double click writes once. Saving sends the ids the form loaded; if the locked set differs, refuse (stale message). Buttons disable with `wire:loading`.
- **Security:** `Gate::authorize('update', $plan)` in `SaveAnnualPlanActivities` and `ReturnAnnualPlanToDraft`; `AnnualPlanPolicy::approve()` = `annual-plans.update` and not the preparer, with `Gate::authorize('approve', $plan)` in `ApproveAnnualPlan`. Repeat the check at the top of each Livewire method (`AuthorizationCoverageTest`); data helpers stay `protected` (`BrowserCallableMethodsTest`). BOLA: activities load through `$plan->activities()->whereKey($ids)`, result ids through the program-framework query above with `whereKey($ids)`; one foreign id rejects the whole batch. `status`, `approved_by`, `approved_at`, `prepared_by` are never read from the request. No money anywhere.
- **Data:** every write in one `DB::transaction`: delete removed, update kept, insert new, one activity record. The four reads of `annual_plans` on the matrix stay four: add `status` to the existing plan-cell select.
- **UI:** tabs **Targets** (existing) and **Activities** (`TABS` + `updatedTab()` as in `proposals/⚡show`); status chip in the `x-ui.detail-header` meta slot with text and icon; **Approve** button; **Return to Draft** modal bound with `wire:model`; grid = activity, 12 month toggles with localized accessible labels, derived implemented months, notes; keyboard-navigable; logical classes only.
- **Notifications:** event keys `annual_plan.approved`, `annual_plan.returned_to_draft`, `annual_plan.activities_updated` (catalog entries per `contracts.md §15` and `§18.1`).
