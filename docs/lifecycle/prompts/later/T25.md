## Goal
On the **Proposal** page, a holder of money permissions enters budget lines per Finance category (HR, Operational, Fixed, Running, Activity) in the proposal's own currency, and sees their total against the requested budget (`proposals.requested_budget`) and, once the agreement exists, against the agreement budget (`donor_proposal.budget`). The breakdown belongs to proposal preparation: it freezes at `submitted` and reopens only when the proposal returns to `proposal draft`. This is money data: nobody without money permissions may query, see or change it. **Amounts in different currencies are never added, converted, netted or compared.**

## Rules
- **Categories:** exactly five (`BudgetCategory`: `hr`, `operational`, `fixed`, `running`, `activity`; string-backed, `HasTranslatedLabel`, `values()`); several lines per category; each line has a description and an amount. Stored values stay English; labels via `$case->label()`.
- **Currency:** a line's currency is the proposal's `requested_currency` (no currency column). While it is null no line can be saved. Changing `requested_currency` while lines exist is refused with a field message, **from every writer** (one shared guard).
- **Totals:** subtotals per category and the total come from SQL `SUM(amount)` or decimal-safe arithmetic, never float accumulation; displayed through `x-ui.money` with the proposal currency; amounts `tabular-nums`.
- **Warnings, never blocks:** total ≠ `requested_budget` → a warning showing both figures; never block a save or a transition. No requested budget → show the total and "no requested budget recorded".
- **Agreement comparison:** read `donor_proposal` through the `DonorProposal` model (not a pivot; see `enums.md`). Compute a difference only when `donor_proposal.currency` equals `requested_currency`; otherwise show both figures, each with its own currency, and say "not compared". Never net across currencies.
- **Edit window:** `allowsBudgetLineEdits()` (exhaustive `match`, no `default`) is true for `concept note`, `concept note review`, `concept note submitted`, `proposal draft`, `proposal review`; false for `submitted`, `on hold`, `approved`, `active`, `completed`, `rejected` (`final reports` is removed, D-02; it is `@deprecated`, false). `submitted → proposal draft` reopens. Confirm the `concept note submitted` reading with Dev 1. **Correct Status** (General Manager and Public Relations Manager) moves a terminal status: the lock simply follows the new status.
- **Who sees and who edits:**
  - **View:** holders of the shared money predicate only. For everyone else the computed property returns nothing **without querying** `budget_lines`, and the section is not rendered (`@can` alone is not enough).
  - **Edit:** `Gate::authorize('update', $proposal)` (`proposals.update`) **and** the money predicate, both inside `SaveProposalBudgetLines`, repeated at the top of the Livewire method (`AuthorizationCoverageTest`).
  - The Public Relations Manager now holds `funding-agreements.view/create/update` (D-31b), so passes the predicate; the 403 test therefore uses a user with `proposals.view` and `proposals.update` granted but **no** money permission, never Super Admin.
- **BOLA:** resolve the proposal from the page's locked id; load existing lines only via `$proposal->budgetLines()->whereKey($ids)`; any foreign line id rejects the whole batch. `proposal_id`, status and currency are never read from input; create through the relation. `#[Fillable(['category','description','amount'])]`.
- **Concurrency:** one `DB::transaction` per save: lock the proposal, lock its lines (`lockForUpdate`), verify the id set equals `expectedLineIds`, then status and currency, delete removed, update kept, insert new, record activity. Any invalid row rolls back the whole batch. A repeated click after success fails gracefully (stale set); the button uses `wire:loading`. Deleting every line is allowed while editable. Notifications `afterCommit`.
- **Audit:** one `proposal.budget_lines_updated` activity per save via `$proposal->recordActivity()`; properties = line counts per category, **no amounts**. If `ProposalRecipients` would notify a watcher without a money permission, keep the event out of notifications and explain how in plan mode. Amounts never appear in activity properties, notifications or tour copy.
- **Section placement:** inside the money-gated `funding` tab, or a new `budget` tab in `TABS` with the same guard in `updatedTab()`. Recommended: inside the `funding` tab (no new tab to guard); Dev 1 may veto.
- **Line cap:** `lines` max 200 (confirm).
- **Data:** FK `budget_lines.proposal_id` cascade (a proposal with an agreement cannot be deleted: `donor_proposal.proposal_id` RESTRICT); table and columns `utf8mb4_unicode_ci`, InnoDB DYNAMIC (`DatabaseEncodingTest`); index (`proposal_id`, `category`); explicit names; `down()` drops the table. New empty table: no pre-check.
- **UI:** a Flux modal (if used) bound with `wire:model="showBudgetLinesModal"`; reuse `x-ui.money`, `x-ui.panel`, Flux inputs; logical classes only (`ms-*`, `pe-*`, `text-start`); full `@php … @endphp` blocks only; page helpers returning data stay `protected`.

Validation (`lang/{en,ar}/proposals.php`): `lines` present, array, max:200; `lines.*.id` nullable integer (ownership enforced in the Action); `lines.*.category` required, `new Enum(BudgetCategory::class)`; `lines.*.description` required string max:255; `lines.*.amount` required numeric min:0 max:999999999999.99.
