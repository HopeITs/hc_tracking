# T40 · One colour language for statuses and alerts · Team B · Phase A (meeting 23 Oct) · 2 days · 2 slices

## Goal
A status or an alert level looks the same on every page: the same tone for "late", "at risk", "done", "validated", in badges, tiles, strips, charts and toasts. Today `x-ui.enum-badge` is the one central mapping (58 views), but 118 view files carry hand-written `bg-status-*` / tone closures (338 occurrences), and several enums are mapped ad hoc. This task gives every status enum a `tone()` and every page a component that reads it.
- **Slice 1:** the tone contract (`Tone` enum, `HasTone`, `tone()` on every status enum, `enum-badge` and `status-pill` read it; alert levels mapped once).
- **Slice 2:** the sweep: replace hand-written tone maps page by page, guard with a test.

## Scope
**In (slice 1):**
- `App\Enums\Tone` (string-backed, lower-case values): `critical`, `warn`, `good`, `info`, `neutral`, `muted`. Each maps to one Tailwind class set in **one place** (`Tone::badgeClasses()`, `Tone::softClasses()`, `Tone::textClasses()`, `Tone::chartColor()` reading the CSS tokens), light + dark.
- `App\Enums\Concerns\HasTone` (interface + default-free `tone(): Tone` on each enum, exhaustive `match`). Applied to: `ProposalStatus`, `ProjectStatus`, `TaskStatus`, `TaskPriority`, `MilestoneStatus`, `MonthlyReportStatus`, `ReportStatus`, `DeliveryState`, `ArStatus`, `RagStatus`, `ActivityStatus`, `ResultType` (neutral/info), `DonorType`, `Period`, and any other enum `enum-badge` already matches.
- `enum-badge` and `status-pill` read `$case->tone()`; their existing visual result stays **the same** for every case (regression test compares the rendered class per case before/after; where two cases of the same meaning differ today, align them and list the change in the handoff).
- Alert priorities (`critical` / `important` / `normal`) and deadline states (overdue / due soon / on track) map to `Tone` in one helper (`App\Support\Tones::forPriority()`, `::forDeadline()`), used by toasts, the bell, the dashboard tiles.
**In (slice 2):** replace every hand-written tone map and raw `bg-status-*` in views and Livewire concerns with the `Tone` helpers or the components; keep semantics (a red stays red). Charts take series colours from `Tone::chartColor()` or the dataviz palette already in `data-viz.css`.
**Out:** new colours or tokens, dark-mode palette changes, brand colours, redesign of any component, enum value changes.

## Rules
- Status is never conveyed by colour alone: every tone use sits next to the label or an `sr-only` text (already the rule; the sweep must not remove labels).
- `match` without `default`; one tone per case; no page-level overrides. A page needing a tone the enum lacks **asks** (escalate), never adds a class.
- Light/dark pairs live only in `Tone` methods; views never write `dark:bg-status-*`.
- Guard test (slice 2, end): a source scan over `resources/views` and `app/Livewire` for `bg-status-|text-status-|border-status-` outside `Tone.php`, `enum-badge`, `status-pill` and an explicit small allow-list (`data-viz.css` consumers). Red until the sweep is complete.
