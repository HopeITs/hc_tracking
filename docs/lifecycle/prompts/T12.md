## Rules
- Levels and scope exactly as §11.2. `SaveResult` derives a proposal root's `program_id`; never from input. On a root save it re-derives `program_id` and cascades to the subtree (as today).
- `contributes_to_result_id`: proposal roots only, pointing to a program-framework result of a program of the proposal's projects; no level restriction.
- Activities may carry indicators like any other level (optional; activities are often procedural steps). RAG rating stays on the calendar year.
- Two editors save under the same parent: the observer re-reads the parent inside the save, so a parent deleted meanwhile fails the FK and returns the "choose another parent" message, never a 500.
- Register the framework edit events (`result.*` on proposals, digest) in T21's `EventCatalog`; if T21 isn't merged, add the keys and tell Dev 3.
- Changing an output with activities to another type is refused. Delete keeps the existing rules (no delete with children or indicators).
- **Editable from `concept note`.** After `submitted`, structural edits (add/move/retype/delete) only by `results.update` holders. Enforced in the actions from the proposal's stored status.
- **Delete proposal:** refused while any indicator in its framework has targets with reports. Otherwise the framework is deleted leaf-first through Eloquent, then `$proposal->delete()` (so `PlanIndicatorSourceObserver` removes targets), all in one transaction under `Activity::withoutRecording` with one `proposal.deleted` event. The existing funding-agreement guard stays. A double click → the second call returns quietly.
- **Milestone link:** `MilestonePolicy::update`; allowed activities per §11.2. Moving a project's program or unlinking a project flags links (`activityLinkIssues()`), never auto-fixes. Observers fire only when `result_id`/`parent_id` is dirty.
- **Program pages** use `programFramework()`: `programs/⚡show::resultRoots()`, `Program::results()` and every "program framework" read; list each one you change. Annual-plan targets may not point at proposal-framework indicators (`chainIssuesFor()`).
- **Every array/map keyed by `ResultType`** gets explicit `activity` and `cross-cutting` arms in the same change (grep all; no `default`). The `parentLevelOf()` `default` arm becomes exhaustive.
- **Activity identity:** an outlined dot and no accent bar (recorded in `components-ui.md`). Cross-cutting shows as a separate group below the tree.
- **Authorization:** results writes keep `results.create/update/delete`; `proposals.update` alone grants nothing. Parent / contributes-to / activity ids are validated server-side against the scope (`Result::where('proposal_id', …)->whereKey($id)`, `programFramework()`). `#[Locked]` ids. The tab is visible to whoever can view the page (incl. T07 reviewers), with no money loaded.
- **Calendar (slice 3):**
  - `activity_kind` is required for activities (default `continuous`). A continuous activity gets a start and end month (all months between scheduled); an event gets one or more separate months.
  - Months outside the proposal's `planned_date_begin`…`planned_date_end` are refused (`month_outside_period`). Weeks 1–5, only for scheduled months.
  - An activity with no scheduled month never appears in the monthly report (T17) and shows a «بلا رزنامة» / "No calendar" badge.
  - Before approval: MEAL + proposal editor (`proposals.update`); after approval: MEAL only (logged).
  - `ShiftActivitySchedulesOnApproval`: a queued, idempotent listener on `ProposalStatusChanged` with `to = approved`. It shifts by (actual − planned start) months once, keeping weeks, and records that the shift was applied (so a re-run is a no-op).
