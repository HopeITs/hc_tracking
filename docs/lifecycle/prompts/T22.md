# T22 · Encrypt uploaded files at rest · B4 · days 2–5 (merged by end of day 5) · 2 slices

## Goal
Every uploaded document is written to disk encrypted (AES-256-GCM through `Illuminate\Encryption\Encrypter`, with a dedicated `FILE_ENCRYPTION_KEY` that is never `APP_KEY`) and decrypted only while the existing protected download and preview routes stream it. Authorization, URLs, upload rules and limits do not change. Later tasks (T07, T17, T19, T31) inherit encryption by storing through `StoredFiles`.
- **Slice 1 (days 2–5):** encrypt on write, decrypt on stream, key handling (config, keyring, errors, `security:reencrypt --files`, `files:decrypt`).
- **Slice 2 (day 5, **on the cut list**):** the resumable command that encrypts existing plaintext files. If the plan is late at CP3 this slice moves after launch; slice 1 must still be merged so new uploads are encrypted from deployment. Keep the command complete and tested so Dev 1 can run it after go-live.

## Human-run steps (Claude never sees or prints the real key)
Claude must not read `.env`, `config('files.encryption.key')` or any key value, and must not print, log, commit or paste one. Tests generate a random key per test. These steps are done by the **developer or Dev 1**, never by Claude:
1. Generate a local key and put it in `.env`: `<php> -r "echo 'base64:'.base64_encode(random_bytes(32)).PHP_EOL;"`. Repeat on staging and production (different keys per environment).
2. Store a copy of the production key **off the server** (D-19; CP6 gate: "encryption key stored off-server").
3. Run `files:encrypt-existing` for real on staging/production (T27 rehearses, T29 runs), after a backup, and `security:reencrypt --files` for any rotation.
4. Run `files:decrypt` on real files.
Claude may run the commands only against the test suite and local masked data, with `--dry-run` first.

## Rules
- **Fail closed.** Every upload stored after deployment is encrypted. With no valid key the upload is refused (message on the `newFile` field, error logged); plaintext is never written as a fallback.
- **Order:** `SecureUpload`, `max:5120`, `mimes`, `extensions` run on the original upload in the component's validation, before `StoredFiles`. Encryption happens only inside `StoredFiles`, after validation. `size` keeps the original byte count (ciphertext is about a third larger and never counts against 5 MB).
- `encryption_key_id` NULL = legacy plaintext, streamed as is until the command encrypts it.
- URLs, route names, download filenames, IDOR guards, `isFundingPaper()` 403, `throttle:files` and all headers (`X-Content-Type-Options: nosniff`, preview `Content-Type`, `Cross-Origin-Resource-Policy`, `Cache-Control: private`, `Content-Security-Policy: sandbox` for images) stay identical. `Gate::authorize('view', $parent)` and the ownership check run first; decrypt only after both pass.
- **Raw bytes:** `$encrypter->encrypt($bytes, false)` / `decrypt($payload, false)`, 32-byte key, cipher `aes-256-gcm` (the GCM tag is the integrity check). Never use the `Crypt` facade or the default encrypter for files; `APP_KEY` and the file key rotate independently.
- `Content-Type` comes from the validated `FileType` (new `FileType::mimeType()`), never from the stored bytes or the client.
- Errors reveal no path and no crypto detail. `Log::error` carries table, row id and key id only. Never log, print or return a key, plaintext or payload (tests, `phpunit.xml`, `.env.example`, exceptions included).
- Wrong key, corrupt file or unknown key id: decrypt **before** building the response, catch `DecryptException`, throw `UnreadableStoredFile` → friendly page; never a raw 500 or a half-sent stream. The Office preview sees a non-OK response and shows its existing error state (no JS change).
- The `local` disk has `'throw' => false`: check every `put/move/delete` return value and abort that file.
- Livewire keeps the plaintext temporary upload in `livewire-tmp`. Delete it after a successful encrypted save (best effort); abandoned ones stay until `files:prune` (24 h). State this residual risk in the handoff.
- Replacing a file: the new upload is encrypted; the old file (plaintext or encrypted) is forgotten after the save, as today.

## Do not
