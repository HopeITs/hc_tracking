# Handoff · W-33 · Extension alert for ending proposals with remaining funds

## Two things Dev 1 should look at

1. **The due-soon machinery could not say what D-60 wants said.** Every `DeadlineCatalog` item ends up with one of four generic sentences — "“X” is due today", "due in N working days" — because `DueSoonScanner` builds the message from the stage, not the item. W-33's whole point is the clause "and its agreement still has funds", which that wording cannot carry. Rather than ship an alert that says only "is due today" (true, and useless), `DeadlineItem` gained an optional **`messageKey`** that `DueSoonScanner` prefers when it is set, taking the same `:subject` and `:date`. One nullable property and one `??`; every existing item is untouched. **It is a change to shared T21 machinery, so it is named here rather than left in the diff.**
2. **The alert collides with the proposal deadline alert, and wins.** `DeadlineCatalog::proposals()` already raises a due-soon item for every proposal nearing its end, to the same two roles. Same subject, same date, same stage, so the ledger keeps one of the two and which one is an accident of order. `items()` now computes the extension items first and passes their proposal ids to `proposals()` as `$except`, so an active proposal with funds left gets W-33's sentence **instead of** the generic one, not as well as. A proposal with no funds left is unaffected.

## Delivered contracts (exactly as on the branch)

### `contracts.md §9` — the setting
`extension_lead_days`, default **60**, in `config/notifications.php` beside the other day counts. Working days, like every count there (`.ai/rules/alerts.md`). Editable on `/admin/notification-settings` as `extensionLead`, validated `between:1,365`, with label `notifications.admin.extension_lead` and hint `…_help`.

### `contracts.md §15.2` — the event
Catalog key **`proposal.ending_with_funds.due`**, module `proposals`, source `scanner`, oversight `$all`.

> The contract names the key `proposal.ending_with_funds`. `DueSoonScanner` looks up `<eventKey>.due` for a catalog-driven item — the convention `department_task.due` / `.overdue` already follows — so the registered key carries the suffix and the `DeadlineItem` carries the prefix. Same key, two halves.

Stages `[extension_lead_days, 0]`: the lead day, then the end date itself.

### The item — `DeadlineCatalog::endingWithFunds()`
Active proposals, **joined** to `donor_proposal` so one without an agreement is excluded by construction, with `AgreementMoney::OUTSTANDING_SQL > 0`, whose `coalesce(extended_date_end, actual_date_end, planned_date_end)` falls inside the window. The money comes from one `leftJoinSub(AgreementMoney::perAgreement())` over all candidates — never a query per row — and no amount leaves the method.

**The remaining-funds rule is `AgreementMoney::OUTSTANDING_SQL`**: `donor_proposal.budget − coalesce(money.m_received_gross, 0)`, floored at 0 — budget the donor has committed and not yet transferred. It is the application's only money-remaining concept, already behind `perAgreement()`, `agreementColumns()` and the finance tables, so W-33 defines nothing new.

Recipients (`DeadlineCatalog::extensionRecipientIds()`): holders of `funding-agreements.view` who are `Financial` or `Public Relations Manager`, never Super Admin (D-20a). Passed as `directUserIds`, not `watcherRoles`, because the contract names a permission the watcher-role path does not check.

### The quick action
`proposal.request_extension` in `QuickActions`, built like `agreement.record`, which is already a redirect rather than a write. Offered on a `proposal` subject when the user holds `proposals.update` **and** the proposal is `active`; running it redirects to `proposals.show?extend=1`, the deep link W-08 already built, and re-checks both conditions first. Labels `notifications.quick.labels.proposal_request_extension`, running message `notifications.quick.opening_extension`.

### Language
`lang/{en,ar}/notifications.php`: `alerts.ending_with_funds` (the sentence), `events.proposal.ending_with_funds.due.{title,body}` (the rules page), the quick-action label and its opening message, and the setting's label and hint. **No figure and no currency in any of them**, in either language.

## Deviations from contracts.md / the prompt

1. **`DeadlineItem::$messageKey` and the `DueSoonScanner` line that reads it** — finding 1. Shared machinery, added because the contract's sentence is otherwise unreachable.
2. **`proposals()` takes `$except`** — finding 2.
3. **The catalog key carries a `.due` suffix** the contract text does not show, because that is what the scanner looks up (above).
4. **`remaining > 0` is the prompt's threshold, not a settled figure.** D-60 is "decided, more discussion pending" and says in as many words that *"the thresholds (days before the end, and the remaining amount) are to be set at the next meeting"*. `> 0` was chosen on the developer's instruction as the widest behaviour, which the meeting can only narrow; narrowing is one `whereRaw`, or a second setting beside `extension_lead_days`. **The 60-day default is in the same position.**
