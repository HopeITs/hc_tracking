# Handoff · W-34b · Tracking-owned programs

Branch: `wave2/W-34b-local-programs` · Owner: Dev 1 · Date: 2026-11-05 · Status: in progress (slice 1/2) · ClickUp: https://app.clickup.com/t/123jdbarcyu · Ruling: **D-68**

## Read this first: the deploy order is not optional

```
php artisan migrate
php artisan programs:import-from-hr --dry-run     # look at it
php artisan programs:import-from-hr --apply       # then this
```

The migration adds the columns **empty** — it deliberately does not read the `hr` connection, because the test suite builds HR's schema per test and a migration touching `hr` would be unrunnable. So between the two commands every program has `name_en = ''` and `slug = NULL`: the Programs page lists blanks and **every `programs/{slug}` route 404s**, because the route key is now that column. Run the import in the same deploy step, before anyone opens the app.

The import is idempotent, so running it again is free.

## What changed in one line

`programs` was a thin mirror of `hchr_programs` under the same id, with its name, code, slug and active flag read live out of HR on every page. It is ours now. Nothing in the application reads a program out of HR except `App\Support\ProgramImport`.

## Delivered contracts (exactly as on the branch)

**Schema** — `contracts.md` §7, block **W-34b (D-68)**; migration `2026_11_05_134235_make_programs_a_tracking_owned_table`:

```
programs   name_en   varchar(255) NOT NULL default ''
           name_ar   varchar(255) null
           code      varchar(50)  NOT NULL default ''
           slug      varchar(255) null, unique `programs_slug_unique`
           is_active boolean      NOT NULL default 1, index `programs_is_active_index`
```

`name_en` and `code` are NOT NULL **with an empty default** so the many places that insert a program row through the query builder keep working; the contract text says so. Every column is pre-checked before the DDL, `down()` drops all five (verified both ways on `hc_tracking_test`), utf8mb4_unicode_ci.

**`App\Support\ProgramImport`** — the only reader of HR's programs:

```php
public const IdHeadroom = 1000;
/** @return array{inserts: Collection<int, stdClass>, updates: Collection<int, non-empty-array{name_en?: string, code?: string, slug?: string, is_active?: bool}>, orphans: Collection<int, stdClass>, kept: Collection<int, array{id: int, ours: string, theirs: string}>} */
public function plan(bool $force = false): array;
/** @return array{inserted: int, updated: int, idFloor: ?int} */
public function apply(bool $force = false): array;
```

- `plan()` writes nothing and is also the **drift report**: HR programs we lack (`inserts`), rows we can still fill from HR (`updates`), our programs HR no longer has (`orphans`, always kept — projects and plans hang off them), and names we hold that differ from HR's (`kept`).
- `apply()` inserts, fills, raises `AUTO_INCREMENT` to `max(our max, HR's max) + 1000` (MySQL only; `idFloor` is null on any other driver), forgets the name lookup, and dispatches `CheckProgramLogframe` for what it inserted.
- A `name_en` already filled in tracking is **never** overwritten without `$force`. Slugs are carried over from HR so existing URLs keep working.

**`php artisan programs:import-from-hr {--dry-run} {--apply} {--force}`** — the command line over that service. `--dry-run` is the default and `--apply` is ignored when both are given.

**`App\Models\Program`** — `#[Fillable(['name_en', 'name_ar', 'code', 'strategy_id', 'strategic_pillar_id', 'manager_id', 'donor_attribution'])]`, `is_active` cast to boolean, `$attributes` mirrors the three column defaults for strict mode. Uses `HasSlug` (`slugSource()` = `name_en`); the old `slug` accessor, `getRouteKeyName()` and the custom `resolveRouteBinding()` are gone.

```php
public static function syncFromHr(): void;              // was: array of newly inserted ids
public static function namesById(): array;              // array<int, string>, current language
public static function nameOf(int $id): string;
public static function codeOf(int $id): string;
public static function idsMatchingName(string $search): array;   // list<int>, either language
public static function idsOrderedByName(): array;                // list<int>
public static function forgetLookup(): void;
public static function options(): Collection;           // select id, name_en, name_ar, manager_id
#[Scope] whereNameLike(Builder, string): void            // plain SQL on both name columns
#[Scope] orderByName(Builder, string $direction = 'asc'): void
#[Scope] active(Builder): void                           // is_active = 1
```

The five statics replace `HrProgram::namesById()` and friends with the same shapes, so each call site changed by class name only. The lookup is one query per request (`spl_object_id(app())` guard, as `RemembersHrLookup`), and `ProgramObserver::saved/deleted` forget it so a rename is visible to the rest of the request.

**`Program::syncFromHr()` returns void and no longer inserts.** All it does is follow HR's Program Manager position for `manager_id` — an HR employee, so still HR's. `SyncProgramsFromHr` middleware keeps calling it once a minute and no longer dispatches anything.

**`contracts.md` §10** gains the W-34b bullet: programs are not part of the HR read model, and no caller may reach `HrProgram` for a name, code or slug.

## Deviations from contracts.md / the prompt

1. **The prompt carried no `[contract]` block** (it said Dev 1 would write it after D-68). I wrote both blocks — §7 and §10 — and the developer approved the exact text before any code. They are the first commit on the branch.
2. **The prompt says §10 "loses the «programs are HR-sourced» sentence".** There is no such sentence in §10; it lived in `.ai/rules/models.md` and the `Program` docblock, both rewritten here. §10 gained the new bullet instead.
3. **`name_en` / `code` are NOT NULL with an empty default**, not bare NOT NULL. Dozens of query-builder inserts of program rows would otherwise fail.
4. **The logframe-gap trigger lives in `ProgramImport::apply()`, not on `Program::created`.** A `created` observer hook fires for every factory-made program and alerted in ~15 unrelated tests; the job belongs with the code that actually creates programs. **Slice 2's `SaveProgram` must dispatch `CheckProgramLogframe` too** — that is the only remaining creator. The daily `DataGapScanner` rule still covers programs with open projects and no framework either way.
5. **`ImportStrategyPillars` and `ImportProgramFramework` no longer auto-create a program.** Both called `syncFromHr()` to conjure a missing row. Under D-68 a program the file names and tracking does not have is drift to report, not something to invent — and the framework command already refuses such a program at its code check, so that call was unreachable. The pillars command reports it as missing, which it already did.
6. **`ProjectDirectoryTest`'s query budget went from 25 to 26.** The name lookup moved from the `hr` connection onto ours; the test counts both, so this is one query relocated, not added. Flat however many projects are listed.

## Follow-ups (not done here)

- **`program_requests` is now pointless and should be retired.** W-34a shipped it as the bridge: a new program name on a location row opens a request, the HR liaison creates the program in HR, `/admin/program-requests` links `hr_program_id`. Under D-68 the program is simply created here. Retiring it means the table, `ProgramRequest`, `ProgramRequestStatus`, `ProgramRequestPolicy`, the `program_request.opened|linked` catalog keys, the `hr_liaison` slot, the `locations_complete` clause that waits on a pending request, and the admin page — its own item with its own `[contract]` text, after slice 2. Left untouched here on purpose.
- **At unification, decide how HR reads our programs** (an API, a view, or a shared store). D-68 defers it and it blocks neither slice.
- **HR and tracking number their rows independently**, and the import matches on the id. That is correct for the existing programs, which were created under HR's ids, and the raised `AUTO_INCREMENT` protects everything new — but it also means a test that inserts an HR program and a tracking program without pinning ids can have them collide at id 1. Two tests in `LogframeGapAlertTest` were silently relying on that coincidence; they now pin the HR id to 9001. Worth remembering when writing any test that needs an HR-only program.
- `center_requests` (W-34c, Dev 1's 4 Nov ruling) is unaffected: HR still owns centers.
