## Three things Dev 1 has to decide on

1. **The `[contract]` text contradicts itself.** It gives `creates` as varchar(20) and names the value `final_report_milestone`, which is 22 characters. The column would reject the value the same paragraph asks for. **Built as varchar(30)**; the contract text needs the same correction.
2. **The approver cannot open the final-report milestone.** Public Relations Manager holds `proposals.update` and so approves proposals, but not `milestones.create`, so `MilestonePolicy::planForProposal` refuses them. Running the listener as the approver — which is otherwise right, and is what makes `created_by` and the authorisation real — therefore failed exactly when the PR Manager was the approver, and failed *silently*, because the action logs and skips. **Resolved on the developer's instruction** by giving `SaveProposalMilestone` a second, Gate-free door for system-created milestones (below), on the same reasoning T33's `ReportTemplatePrefiller` already runs on: a system rule the PR Manager configured is not a person's request. The alternative was granting PR Manager `milestones.create`, which widens them everywhere.
3. **The milestone is anchored to the proposal's period, not to the approval.** `SaveProposalMilestone::checkPeriod()` requires a milestone's `planned_start_date` to fall inside the proposal's period, so "today + 30 days" was rejected outright on any proposal that had already ended. The template's `due_offset_days` now counts from the **end of the proposal's period** (actual dates when present, else planned), never earlier than today. A review task still counts its offset from the effective date of the move, as the prompt says — the two anchors differ on purpose, and the prompt only specified the task one.

## Delivered contracts (exactly as on the branch)

### Schema — `2026_11_04_124148_create_proposal_stage_task_templates_table`
```
proposal_stage_task_templates
  id · status varchar(30) · department_id unsigned big int (HR, no FK) · kind varchar(30)
  creates varchar(30) default 'task'        -- 30, not the contract's 20; see finding 1
  title_en · title_ar · description_en null · description_ar null
  due_offset_days smallint default 0 · is_active bool default 1
  repeat_on_reentry bool default 0          -- the prompt's own re-entry rule needs it
  sort_order unsigned small int default 0 · timestamps
  unique  (status, department_id, kind, title_en)  `stage_task_templates_unique`
  index   (status, is_active)               `stage_task_templates_status_index`

tasks.stage_template_id       FK → templates, null, nullOnDelete, indexed
milestones.stage_template_id  FK → templates, null, nullOnDelete, indexed
```
`stage_template_id` is in `Task`'s `#[Fillable]`. `up()` and `down()` both pre-check, so a partial run is safe.

### `App\Enums\StageTemplateCreates`
`Task = 'task'`, `FinalReportMilestone = 'final_report_milestone'`; `values()`, `HasTranslatedLabel`. Labels in `lang/{en,ar}/enums.php` under `stage_template_creates`.

### `App\Models\ProposalStageTaskTemplate`
`#[Scope] forStatus(Builder $query, ProposalStatus $status)` — active templates of that status, by `sort_order` then `id`. `title` and `description` accessors give the interface language falling back to English. `UNIQUE_INDEX` constant. Casts `status`, `kind`, `creates`. Policy `ProposalStageTaskTemplatePolicy`, all abilities on `stage-task-templates.manage`.

### `App\Support\EmployeeProfile::managerOfDepartment(int $departmentId): ?int` — **a §10 addition, unauthorised**
The employee whose current HR position in that department sits at job level **grade 5, "Department Manager"** (D-65). Several holders is normal — Finance has three on the live HR data — so the tie-break is the one `holderOfPosition()` already uses, the latest contract start date, and an ambiguous department is logged rather than picked silently. Reads the lookup `EmployeeProfile` already holds: no new HR query.

**W-12's `[contract]` block does not authorise a §10 change, so this needs Dev 1's sign-off.** It is here because the final-report milestone needs a person and the column is NOT NULL while D-33 forbids assigning one; the department's manager is the answer the developer chose, and it is read from HR rather than invented.

> **W-14 implements D-65's scope rule and must call this method.** Writing a second definition of "department manager" is exactly what the quality bar's one-rule-one-definition line forbids.

### `App\Actions\Proposals\CreateStageTasks::handle(Proposal $proposal, ProposalStatus $status): list<int>`
Signature exactly as the contract. Per active template of the status: a `Task` with the proposal as `source`, the department, the kind, the template's title and description, `requested_on` today, `due_date` from the offset, `stage_template_id`, and **no assignee** (D-33). A `final_report_milestone` template calls `SaveProposalMilestone::addFinalReportFromTemplate()` instead.

Idempotency is the pair (proposal, template): an ordinary template is skipped once its task exists; a `repeat_on_reentry` one is skipped only while its last task is still open, so a re-entry after the work is done creates a fresh task. The final-report template keys on the proposal's one `is_final_report` milestone, which `SaveProposalMilestone` enforces anyway.

It never throws at the caller: a department with no manager, a proposal with no period, or a refused milestone is logged and skipped, and the rest of the templates still run.

### `App\Actions\Milestones\SaveProposalMilestone` — one new door
```php
public function addFinalReport(Proposal $proposal, array $input): Milestone;              // unchanged, authorises
public function addFinalReportFromTemplate(Proposal $proposal, array $input): Milestone;  // new, no Gate
```
Both call one private `writeFinalReport(..., bool $authorize)`, so the one-milestone rule, the validation and the task it creates have a single definition. Finding 2 is why the second door exists.

### `App\Listeners\CreateStageTasksOnStatusChanged`
Queued, auto-discovered, built on `PrefillReportTemplates`: `shouldQueue()` true only when the status has templates, `tries = 3`, backoff `[10, 60, 300]`, failures reported rather than thrown when the queue runs inline. **It authenticates as `$event->actorId` for the duration and restores the previous user afterwards** — `created_by` and the ordinary task writes need a user, and a queued job has none.
