## Goal
Every proposal carries **location rows** (D-62): `is_new` · city* · [program] · [responsible] · [centers] · ➕. Bracketed fields are optional until approval and required at `approved` (requirement key `locations_complete`). On approval the writer **materialises** the missing projects from the rows inside the same transaction, and asks HR for programs that do not exist yet through `program_requests`. The `projectIds` picker disappears from the proposal form; linking projects by hand becomes a thin wrapper used only by admin flows.
- **Slice 1 (Dev 1):** schema, models, factories, `SaveProposal` accepts `locations[]`, backfill command.
- **Slice 2 (Dev 1):** requirement keys, `MaterialiseProposalLocations` inside `ApproveProposal`, events, notifications.
- **Slice 3 (Dev 2):** rows table in the proposal form, Locations chapter on the proposal page, approve preview, `admin/program-requests`.

## Rules (all slices)
- Tables exactly as `W-34.md` §1: `proposal_locations` (unique `(proposal_id, city_id, program_id)` with `program_id` nullable, so one "no program yet" row per city), `proposal_location_centers`, `program_requests` (`status` pending|created|declined, `hr_program_id` null). HR ids carry **no FK**; `program_id` and `project_id` do.
- `is_new` means "no project exists yet for this row"; when a row is not new the user picks an existing open project of that city/program (W-01 picker) and the row stores `project_id`.
- `SaveProposal` validates rows as a whole: ≥ 1 row at creation; cities distinct per program; a center must belong to the row's city (HR lookup, in memory); a responsible must be an active employee. Rows are replaced atomically (delete-insert under the proposal lock) and `ProposalLocationsChanged` fires after commit with the diff (added/removed/changed counts, no names).
- `locations` key replaces `linked_project` on `concept note → concept note review`; `locations_complete` is checked by `ApproveProposal` (every row has program **or** a pending program request, responsible, and either `project_id` or `is_new`). The `TransitionProposal` budget/dates keys are unchanged.
- `MaterialiseProposalLocations` runs inside `ApproveProposal`'s transaction **before** `ApproveProjectFromProposal`: for each `is_new` row with a program → `SaveProject` (draft, city, center or host center per W-01, owner = responsible's user or the actor when the responsible has no account, sectors empty) then link; rows whose program is only requested stay unmaterialised and the proposal still approves (the project is created when HR links the program, key `program_request.linked`). Idempotent: a row with `project_id` is skipped. Duplicate open project in the same (center/city, program) → **link** the existing open project instead of creating one, and add a warning to `ApprovalResult::$warnings` (`location_linked_existing`).
- `LinkProposalProject` / `UnlinkProposalProject` keep their signatures and become wrappers that also insert/delete the matching location row.
- `program_requests` are opened by `SaveProposal` when a row names a program that is not in `programs` (free text `requested_name`), notify the HR-liaison slot (`Slots`, key `program_request.opened`), and are listed at `/admin/program-requests` (`programs.update` holders): the admin picks the HR program once it exists → `status = created`, `hr_program_id` set, the rows updated, projects materialised if the proposal is already approved. Declining writes a reason and notifies the proposal owner.
- Backfill command `proposals:backfill-locations {--dry-run} {--apply}`: one row per linked project (city, program, center, owner, `is_new = false`, `project_id`), idempotent, prints counts.
- UI (slice 3, `W-34.md` §5): rows table in the form (Alpine repeater bound to `locations`, one validation summary at the top naming the first invalid row), "Locations" chapter on the proposal page (rows, badges new/linked/awaiting program), approve modal preview "will create N projects, link M, wait for K program requests", `admin/program-requests` page with the standard register anatomy.
- No money anywhere in rows, events or notifications.
