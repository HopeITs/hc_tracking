# W-34 · Proposal location rows and projects created on approval

Ruling D-62 (29 Oct 2026). Owner: Team A (Dev 1 + Dev 2). Size XL, split in two deliverables so the second can wait for HR.

## 0. The conflict to settle first

D-62 says programs and projects are owned by Tracking, HR reads them. Today the opposite is frozen:

- `programs` rows mirror `hchr_programs` under the **same id**; the name is not stored here (decision of 23 Sep 2026, rule `concerns-factories.md`). `Program::syncFromHr()` runs from `SyncProgramsFromHr` middleware.
- The `hr` connection is **read-only**; `HrModel::save()` throws. Tracking cannot push a program into HR.
- `projects` are already created only in Tracking (`SaveProject`). HR has no projects table of its own.

So "projects from Tracking" is already true. "Programs from Tracking" needs the HR app to change where it reads programs from. That is outside this repo.

**Split:**

| Part | What | Needs |
|---|---|---|
| **W-34a** | Location rows on the proposal, projects created on approval, `is_new` rows that need a program become a **program request** shown to HR. Programs stay HR-mirrored. | nothing outside this repo |
| **W-34b** | `programs` becomes a local table (id, name_en, name_ar, code, is_active) that HR reads; the mirror direction flips. | decision **D-68** (Shadi + HR developer) and an HR-side change |

W-34a ships in this wave. W-34b is listed in "Later" until D-68 is answered.

## 1. Schema (W-34a) — contracts.md §7 addition

```
proposal_locations
  id
  proposal_id        FK proposals cascadeOnDelete
  city_id            unsigned big int, HR id, no FK, NOT NULL
  program_id         FK programs nullOnDelete, NULL allowed
  responsible_employee_id  unsigned big int, HR id, no FK, NULL allowed
  is_new             boolean default false   -- "no program/center exists yet for this row"
  project_id         FK projects nullOnDelete, NULL  -- filled on approval (or when linked to an existing project)
  sort               unsigned small int
  timestamps
  unique (proposal_id, city_id, program_id)  -- program_id NULL rows are not covered by the unique index; app rule: at most one NULL-program row per city

proposal_location_centers
  proposal_location_id  FK proposal_locations cascadeOnDelete
  center_id             unsigned big int, HR id, no FK
  primary (proposal_location_id, center_id)

program_requests                      -- only for is_new rows without a program
  id
  proposal_location_id  FK cascadeOnDelete, unique
  name_en, name_ar      string
  status                string(20): pending | created | declined
  hr_program_id         unsigned big int null  -- set when HR creates it and PR Manager links it
  requested_by          FK users nullOnDelete
  timestamps
```

- `project_proposal` pivot **stays**. A location row with `project_id` is the same link; `Proposal::projects()` keeps working for everything downstream (approval, aggregation, M&E).
- `projects.city_id` stays required; `projects.center_id` nullable (T30). W-01 adds `host_center_id`. A row with several centers creates **one project per center** (one open project per center + program, contracts §3); a row with no center creates one project on `city_id` only (W-01 rule: physical center or host center, host = the row's assigned center per D-55).
- Morph keys: `proposal_location`, `program_request` (AppServiceProvider + MorphMapTest). Both record activity on the proposal (`RecordsParentActivity`).

## 2. Requirement keys — contracts.md §2 change

| Transition | Today | After |
|---|---|---|
| `concept note → concept note review` | `linked_project`, `donor`, `planned_dates` | `locations` (≥ 1 row with a city), `donor`, `planned_dates` |
| `proposal review → submitted` | `budget`, `planned_dates`, `target_beneficiaries` | unchanged |
| `submitted → approved` (`ApproveProposal`) | ≥ 1 linked project | `locations_complete`: every row has program **and** responsible **and** (center or `is_new`), and no `program_requests` still `pending` |

`linked_project` key and `UnlinkProposalProject`/`LinkProposalProject` are kept for one release behind the rows (linking a project = a row with `project_id`), then removed. `TransitionProposal::unmetRequirement()` gets the two new keys; messages `proposals.locations_required`, `proposals.locations_incomplete`.

## 3. Writers

- `SaveProposal`: accepts `locations[]` (`city_id`, `program_id?`, `responsible_employee_id?`, `center_ids[]`, `is_new`, `new_program_name_en?/ar?`). Validation: city active in HR; centers belong to the city; program exists; responsible is an active HR employee; `is_new` + no program → name required, creates/updates the `program_requests` row. Rows are replaced as a set inside the proposal transaction (diff by id, delete removed).
- `ApproveProposal` (contracts §6 signature unchanged): after the proposal row is written and before `approveProjects()`, call **`MaterialiseProposalLocations`** (new action, `app/Actions/Proposals/`) inside the same transaction:
  1. for each row without `project_id`: find an open project per (`center_id ?? city_id`, `program_id`) via `Project::openProjectFor()`; reuse it, else create through `SaveProject` with `user_id` = row responsible (owner assignment starts `pending`, as today), name default "Program — Center/City";
  2. write `project_id` on the row and attach `project_proposal`;
  3. `is_new` rows whose program request is not `created` block approval (handled by the requirement above, so here it is an assertion).
  Then `approveProjects()` runs over the union as today. Status writers list (§4) is unchanged: `MaterialiseProposalLocations` creates drafts only; `ApproveProjectFromProposal` still moves them.
- `LinkProposalProject` / `UnlinkProposalProject`: become thin wrappers that add/remove a row with `project_id` (city/program/center copied from the project).

## 4. Events and notifications (§5, §15.2)

- `ProposalLocationsChanged(proposalId, actorId)` — no notification, activity only.
- `program_request.opened` → PR Manager slot + HR mailbox slot (new slot in `Slots`): "Proposal X needs program «name» in HR". `program_request.linked` → proposal owner.
- W-35 reuses the rows: scanner rule `responsible_inactive` over `proposal_locations.responsible_employee_id` and `projects.user_id`.

## 5. UI

- `proposals/⚡form` (W-10 order): the city multi-select is replaced by a **rows table**: `is_new` ☐ · city* · program · responsible · centers · ➕. Centers select filtered by the row's city, programs from `Program::options()`, responsible from `HrEmployee` search. Optional columns show a dot "required at approval".
- `proposals/⚡show`: a "Locations" chapter listing the rows with their project badge (none / draft / approved / active) and the program request state.
- Approve modal: preview lists what will be created ("2 projects will be created, 1 reused") using `MaterialiseProposalLocations::preview()`.
- Donors/HR: `admin/program-requests` page (PR Manager, `programs.manage`): pending requests, "Mark created" asks for the HR program id and links it (`program_requests.hr_program_id`, row `program_id`). Until W-34b this is the only bridge.

## 6. Data migration

- Backfill one row per existing `project_proposal` link: city/program/center from the project, responsible = `projects.user_id`, `project_id` set, `is_new` = false. Print counts.
- Proposals with no link get no row; they will fail the `locations` key on their next transition, which is intended (same as `linked_project` today).
