# W-34 · صفوف مواقع الـ Proposal وإنشاء المشاريع عند الموافقة

الرد D-62 (29/10/2026). المالك: Team A (Dev 1 + Dev 2). الحجم XL، مقسوم إلى جزأين حتى ينتظر الثاني HR.

## 0. التعارض الذي يجب حسمه أولاً

D-62 يقول: البرامج والمشاريع ملك Tracking والـ HR يقرأها. اليوم العكس مثبّت:

- صفوف `programs` مرآة لـ `hchr_programs` **بنفس الـ id**، والاسم غير مخزّن عندنا (قرار 23/09/2026، قاعدة `concerns-factories.md`). `Program::syncFromHr()` يعمل من middleware `SyncProgramsFromHr`.
- اتصال `hr` **للقراءة فقط**؛ `HrModel::save()` يرمي خطأ. Tracking لا يستطيع دفع برنامج إلى HR.
- المشاريع تُنشأ أصلاً في Tracking فقط (`SaveProject`). لا جدول مشاريع في HR.

إذاً "المشاريع من Tracking" محقق أصلاً. أما "البرامج من Tracking" فيحتاج تغيير تطبيق HR ليقرأ البرامج من عندنا، وهذا خارج هذا المستودع.

**التقسيم:**

| الجزء | ماذا | يحتاج |
|---|---|---|
| **W-34a** | صفوف المواقع على الـ Proposal، إنشاء المشاريع عند الموافقة، الصف `is_new` الذي يحتاج برنامجاً يصبح **طلب برنامج** يظهر لـ HR. البرامج تبقى مرآة لـ HR. | لا شيء خارج هذا المستودع |
| **W-34b** | `programs` يصبح جدولاً محلياً (id, name_en, name_ar, code, is_active) يقرأه HR؛ اتجاه المرآة ينعكس. | قرار **D-68** (شادي + مطوّر HR) وتغيير في جهة HR |

W-34a يُسلَّم في هذه الموجة. W-34b يبقى في "لاحقاً" حتى يُجاب D-68.

## 1. المخطط (W-34a) — إضافة إلى contracts.md §7

```
proposal_locations
  id
  proposal_id        FK proposals cascadeOnDelete
  city_id            unsigned big int، id من HR، بلا FK، NOT NULL
  program_id         FK programs nullOnDelete، يقبل NULL
  responsible_employee_id  unsigned big int، id من HR، بلا FK، يقبل NULL
  is_new             boolean default false   -- "لا برنامج/مركز لهذا الصف بعد"
  project_id         FK projects nullOnDelete، NULL  -- يُملأ عند الموافقة (أو عند الربط بمشروع موجود)
  sort               unsigned small int
  timestamps
  unique (proposal_id, city_id, program_id)  -- صفوف program_id = NULL خارج الفهرس؛ قاعدة تطبيق: صف واحد بلا برنامج لكل مدينة

proposal_location_centers
  proposal_location_id  FK proposal_locations cascadeOnDelete
  center_id             unsigned big int، id من HR، بلا FK
  primary (proposal_location_id, center_id)

program_requests                      -- فقط لصفوف is_new بلا برنامج
  id
  proposal_location_id  FK cascadeOnDelete، unique
  name_en, name_ar      string
  status                string(20): pending | created | declined
  hr_program_id         unsigned big int null  -- يُضبط عندما ينشئه HR ويربطه PR Manager
  requested_by          FK users nullOnDelete
  timestamps
```

- الـ pivot `project_proposal` **يبقى**. صف الموقع الذي له `project_id` هو نفس الربط؛ `Proposal::projects()` يبقى يعمل لكل ما بعده (الموافقة، التجميع، MEAL).
- `projects.city_id` يبقى إجبارياً؛ `projects.center_id` يقبل NULL (T30). W-01 يضيف `host_center_id`. الصف الذي فيه عدة مراكز ينشئ **مشروعاً لكل مركز** (مشروع مفتوح واحد لكل مركز + برنامج، contracts §3)؛ الصف بلا مركز ينشئ مشروعاً واحداً على `city_id` فقط (قاعدة W-01: مركز فيزيائي أو host center، والـ host = المركز المعيَّن في الصف حسب D-55).
- مفاتيح morph: `proposal_location` و`program_request` (AppServiceProvider + MorphMapTest). كلاهما يسجّل النشاط على الـ Proposal (`RecordsParentActivity`).

## 2. مفاتيح المتطلبات — تغيير في contracts.md §2

| الانتقال | اليوم | بعد |
|---|---|---|
| `concept note → concept note review` | `linked_project`, `donor`, `planned_dates` | `locations` (صف واحد على الأقل فيه مدينة)، `donor`, `planned_dates` |
| `proposal review → submitted` | `budget`, `planned_dates`, `target_beneficiaries` | بلا تغيير |
| `submitted → approved` (`ApproveProposal`) | مشروع مرتبط واحد على الأقل | `locations_complete`: كل صف فيه برنامج **و**مسؤول **و**(مركز أو `is_new`)، ولا يوجد `program_requests` ما زال `pending` |

المفتاح `linked_project` و`UnlinkProposalProject`/`LinkProposalProject` يبقيان إصداراً واحداً خلف الصفوف (ربط مشروع = صف له `project_id`) ثم يُحذفان. `TransitionProposal::unmetRequirement()` يأخذ المفتاحين الجديدين؛ الرسائل `proposals.locations_required` و`proposals.locations_incomplete`.

## 3. الـ Writers

- `SaveProposal`: يقبل `locations[]` (`city_id`, `program_id?`, `responsible_employee_id?`, `center_ids[]`, `is_new`, `new_program_name_en?/ar?`). التحقق: المدينة فعّالة في HR؛ المراكز تتبع المدينة؛ البرنامج موجود؛ المسؤول موظف HR فعّال؛ `is_new` بلا برنامج ← الاسم إجباري وينشئ/يحدّث صف `program_requests`. الصفوف تُستبدل كمجموعة داخل transaction الـ Proposal (مقارنة بالـ id، حذف المحذوف).
- `ApproveProposal` (توقيع contracts §6 بلا تغيير): بعد كتابة صف الـ Proposal وقبل `approveProjects()` يستدعي **`MaterialiseProposalLocations`** (action جديد في `app/Actions/Proposals/`) داخل نفس الـ transaction:
  1. لكل صف بلا `project_id`: ابحث عن مشروع مفتوح لـ (`center_id ?? city_id`, `program_id`) عبر `Project::openProjectFor()`؛ أعد استخدامه، وإلا أنشئه عبر `SaveProject` بـ `user_id` = مسؤول الصف (تعيين المالك يبدأ `pending` كما اليوم)، الاسم الافتراضي "Program — Center/City"؛
  2. اكتب `project_id` على الصف واربط `project_proposal`؛
  3. صفوف `is_new` التي طلب برنامجها ليس `created` تمنع الموافقة (يعالجها المتطلب أعلاه، فهنا مجرد assertion).
  ثم يعمل `approveProjects()` على المجموع كما اليوم. قائمة كتّاب الحالة (§4) بلا تغيير: `MaterialiseProposalLocations` ينشئ drafts فقط؛ `ApproveProjectFromProposal` يبقى هو من يحرّكها.
- `LinkProposalProject` / `UnlinkProposalProject`: يصبحان غلافين رقيقين يضيفان/يحذفان صفاً له `project_id` (المدينة/البرنامج/المركز تُنسخ من المشروع).

## 4. الأحداث والإشعارات (§5، §15.2)

- `ProposalLocationsChanged(proposalId, actorId)` — بلا إشعار، نشاط فقط.
- `program_request.opened` ← مقعد PR Manager + مقعد بريد HR (مقعد جديد في `Slots`): "الـ Proposal X يحتاج برنامج «الاسم» في HR". `program_request.linked` ← مالك الـ Proposal.
- W-35 يعيد استخدام الصفوف: قاعدة scanner `responsible_inactive` على `proposal_locations.responsible_employee_id` و`projects.user_id`.

## 5. الواجهة

- `proposals/⚡form` (ترتيب W-10): الـ multi-select للمدن يُستبدل بـ**جدول صفوف**: `is_new` ☐ · المدينة* · البرنامج · المسؤول · المراكز · ➕. اختيار المراكز مفلتر بمدينة الصف، البرامج من `Program::options()`، المسؤول من بحث `HrEmployee`. الأعمدة الاختيارية تعرض نقطة "إجباري عند الموافقة".
- `proposals/⚡show`: فصل "Locations" يعرض الصفوف مع شارة المشروع (لا شيء / draft / approved / active) وحالة طلب البرنامج.
- modal الموافقة: المعاينة تعرض ما سيُنشأ ("سيُنشأ مشروعان، ويُعاد استخدام واحد") عبر `MaterialiseProposalLocations::preview()`.
- الإدارة: صفحة `admin/program-requests` (PR Manager، صلاحية `programs.manage`): الطلبات المعلّقة، زر "تم الإنشاء" يطلب id برنامج HR ويربطه (`program_requests.hr_program_id`، `program_id` على الصف). حتى W-34b هذا هو الجسر الوحيد.

## 6. ترحيل البيانات

- إنشاء صف لكل ربط `project_proposal` موجود: المدينة/البرنامج/المركز من المشروع، المسؤول = `projects.user_id`، `project_id` مضبوط، `is_new` = false. طباعة الأعداد.
- الـ Proposals بلا ربط لا تأخذ صفاً؛ ستفشل مفتاح `locations` عند انتقالها التالي، وهذا مقصود (كما `linked_project` اليوم).

## 7. الاختبارات

- `ProposalLocationsTest`: حفظ الصفوف، قاعدة فرادة المدينة/البرنامج، المراكز تطابق المدينة، `is_new` يحتاج اسماً، مفاتيح المتطلبات على الانتقالين.
- `MaterialiseProposalLocationsTest`: إعادة استخدام مشروع مفتوح، مشروع لكل مركز، الصف بلا مركز ينشئ على المدينة، تعيين المالك pending، idempotent عند استدعاء موافقة ثانٍ، الحجب بطلب برنامج معلّق.
- `ProposalStatusWriteGuardTest`: توسيع الفحص إلى الـ action الجديد (يجب ألا يكتب `status`).
- `ProgramRequestTest`: فتح ← مفاتيح الإشعار، الربط يضبط `program_id` على الصف.
- اختبار ترحيل الـ backfill على fixtures (الصفوف == الروابط).
