### Behaviour facts for downstream
- **Every agreement belongs to one donor-approved proposal and carries that proposal's donor** (composite FK from T03 + server write). A forged `agreementDonorId` is ignored (the property no longer exists).
- **Generated rows**: `source = 'auto'`, `installment_id` set, `payment_amount`/currency/`scheduled_date` from the installment; `transfer_date`, `arrival_date`, `receive_date`, received/net amounts, `account_id` empty; `fees`, `exchange_rate`, `ar_status` at their column defaults. Created inside `Activity::withoutRecording`; one `transfer.generated` activity (module `transfers`, properties `{label, count}`, no amount, actor = null when queued) is recorded on the first generated row per run.
- **`FundingAgreementRecorded(int $fundingAgreementId /* donor_proposal.id */, int $proposalId, ?int $actorId)`**: dispatched after commit by `SaveFundingAgreement` on create only (never on a refused save or an update).
- **`transfer.generated` recipients**: Financial (module watcher) + General Manager (`ManagementOnly` oversight). To make oversight apply, the catalog entry `transfer.generated` now carries `activity: 'transfer.generated'` (one-line change in `EventCatalog`, key unchanged). The activity and the notification text carry no amount for anyone.
- Self-funded (`donors.is_internal`) proposals may keep a schedule but never get transfers. A proposal that is not donor-approved gets none either.
- The form saves agreement + schedule in one transaction. Zero schedule rows on create is allowed (schedule can be added later); clearing an existing schedule is refused (`installments_required`); a legacy agreement with only manual transfers is saved without a schedule and its rows are untouched.
- Editing an installment (same `sequence`) does not touch its generated transfer; a new sequence adds exactly one transfer; a removed sequence deletes its generated transfer only while that transfer has no actual data.
- **Sum ≠ budget** is a warning the user confirms (`confirmInstallmentSum`), enforced in the form; `SaveAgreementInstallments` itself never blocks on it.
- `Tranches::timing()`: for a sent, not yet received transfer the "in transit" days run from the sent date to `arrival_date` when set, else to today. `state()` / `stateSql()` are unchanged (decision: a transfer that has arrived but is not received stays `transit`; see Deviations).

## Deviations from contracts.md / the prompt
1. **`state()` / `stateSql()` not changed for `arrival_date`.** The prompt says to update both so "in transit lasts until arrival". Dev (at the keyboard) chose to keep an arrived-but-not-received transfer in `transit` (no sixth state, no vocabulary change); only `Tranches::timing()` uses the arrival date. The parity test (`GenerateExpectedTransfersTest`) pins both.
2. **No policy class for `FundingAgreementInstallment`.** It follows `DonorProposal`: an entry in `PolicyCoverageTest::modelsGuardedWithoutPolicy()` (module `funding-agreements`). It does not use `TracksActivity`: the schedule change is one `donor_proposal.updated` activity (not notified) written by `SaveAgreementInstallments`, to avoid a per-row catalog key.
3. **`EventCatalog` `transfer.generated`** got `activity: 'transfer.generated'` (see above). Dev 1 to confirm; no key renamed.
4. **`ActionAuthorizationTest`**: the `SaveAgreementInstallments` stub exemption is removed; `GenerateExpectedTransfers` is a documented system action (new `systemActions()` list + a test that it never reads the signed-in user). The stub test is now a loop instead of a dataset (Pest rejects an empty dataset).
5. **T03 test fix**: `ProposalDonorSchemaTest` "unique index…" needed `->values()` (key order depended on `information_schema` row order); its "agreement takes its donor from the proposal" test now uses a donor-approved proposal.
6. **Pre-fill / schedule are optional on create.** The prompt does not say whether a new agreement must carry a schedule; a schedule is optional on create and required to stay non-empty once saved. Dev 1 to confirm.
7. The race test cannot keep the competing row after the rollback (same connection); it asserts the friendly message, no 500 and zero agreements.
8. Not done here: unreachable multi-agreement UI cleanup (co-funder lists, `others` currencies), per T03 follow-up.
