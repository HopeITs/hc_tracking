- `effective()` merges `NotificationSettings` key `event_overrides`: `enabled` (only an explicit `false` disables), `importance` (an unknown value is ignored), `oversight_roles` (non-strings, `''` and `Super Admin` dropped). Unknown keys in the overrides are ignored.

**`App\Notifications\Recipients\OversightRecipients`** (`final`)
```php
public function userIdsFor(string $eventKey, ?int $projectId = null): array;  // list<int>, sorted
public function meal(?int $projectId = null): array;                          // MEAL role + user of MealCoverage::responsibleFor($project)
public function management(): array;                                          // General Manager holders
public function departmentUserIds(int $departmentId): array;                  // EmployeeProfile::employeeIdsInDepartment → users
```
- `userIdsFor()`: `all` = meal + management, `management_only` = management, `none` = `[]`; `[]` for a disabled or unknown key. The key's effective `oversight_roles` join **management** (so they apply to `all` and `management_only`). Deleted roles are skipped. Any user holding `Super Admin` is removed, even with another oversight role (D-20a).
- No officer when `$projectId` is null, the project is missing, or `responsibleFor()` returns null / an employee with no account → MEAL role holders only.
- Department head: HR `departments` has no head column; a head is a member when their position's `department_id` is the department. Nothing to escalate.

**`RecipientResolver::resolve()`** (oversight step)
1. `$key = EventCatalog::keyForActivity($activity->event)`. Not a catalog movement → routing unchanged.
2. Catalog event disabled → `new ResolvedRecipients([])` (nobody, direct included).
3. Enabled + `immediate` → `OversightRecipients::userIdsFor($key, $projectId)` appended to the candidates, **not** to `$direct`: view permission and mutes apply to them; direct still wins (one notification per person, keyed by user id). `digest` → nothing to oversight now (slice 2 daily summary).
4. `$projectId` = `subject_id` when `subject_type = 'project'`, else `properties.project_id` when numeric, else null. **Modules whose subject is not a project should record `project_id` in the activity properties** so the project's MEAL officer is reached.

## How a task registers or wires a key
1. The key is already in `EventCatalog::all()` (its module group). If your sibling prompt names a key that is not there, add one entry to the same group and tell Dev 3; never rename.
2. Emit it: record an activity whose `event` equals the entry's `activity` (default = the key), or, for `listener`/`scanner` keys, pass ids yourself. You may adjust your own entry's `direct`/`activity`/`event` fields to match what you emit; importance, oversight and critical are contract (§15.2).
3. Put `project_id` in the activity properties when the subject is not a project.
4. Replace the generic `events.{key}.body` text with your real sentence (keep `title`; en + ar; same placeholders in both).
5. Run `EventCatalogTest`, `EventCatalogCoverageTest`, `LocalizationTest`.

# Slice 2a · per-project calendar and daily scanners (2026-10-14)

## Delivered contracts
**`WorkingCalendar::forProject(Project $project): WorkingCalendar`** (§9, D-22) — same API over `projects.working_days` (sorted, de-duplicated ISO days). `null`, `[]`, or any value outside int 1–7 → the global calendar, no exception. No query (reads the loaded attribute). Constructor gained an optional `?array $days = null` after `NotificationSettings`; container resolution unchanged.

**Scanners** (all in `config/notifications.php` `scanners.daily`, i.e. `notifications:scan daily` at 06:00; every one skips non-working days and goes through `AlertDispatcher`):

| Scanner | Catalog key | Ledger rule · stage | Direct | Non-direct | Message |
|---|---|---|---|---|---|
| `ProjectDatesScanner` | `project.started` / `project.ended` | `project_started` / `project_ended` · the date | owner (`projects.user_id`) + program manager (`programs.manager_id`) | oversight (`userIdsFor($key, $projectId)`) | `notifications.alerts.project_started|project_ended`, Info |
| `OnHoldReminderScanner` | `proposal.on_hold_reminder` | `on_hold_reminder` · `status_remind_on` | owners of the linked projects | `proposals.update` holders (never Super Admin) + oversight | `notifications.alerts.on_hold_reminder`, Important |
| `OversightDigestScanner` | every enabled `digest` key | `oversight_digest` · today | the oversight user (kind `digest`, module `system`) | — | `notifications.digests.oversight` |

- **Project dates:** active projects only; window per project = (its previous working day, today], computed with `forProject()`; a project scanned on a day that is not its working day waits. Start is skipped when the latest `project.activated` activity **or** `project.status_changed` with `changes.status[1] = active` is dated after `start_date` (works before and after T08).
- **On hold:** `status = on hold` and `status_remind_on <= today` (missed dates are caught up). Leaving hold drops it from the query; a new date re-arms (new stage).
- **Oversight digest:** window = [previous working day 00:00, today 00:00) (Monday covers Fri–Sun). Counts activities whose event is the `activity` of an enabled key with effective importance `digest` (overrides apply). Per user: own movements dropped; per module, `RecipientFilter` (view permission + mutes) decides. One row per user, params `count`, `date`, `counts = {event_counts: {key: n}}` (sorted by count). Zero → nothing.
- **New presenter param type** `['event_counts' => [key => n]]`: renders "2 × Project created, 1 × …" from `events.{key}.title` in the reader's language (`digests.oversight_line`).
- `RecipientResolver::projectIdOf()` is now public (reused by the digest; one definition).
- Disabled event → the scanner sends nothing (direct included).

**Lang** (`lang/{en,ar}/notifications.php`): `alerts.project_started`, `alerts.project_ended`, `alerts.on_hold_reminder`, `digests.oversight`, `digests.oversight_line`.
