### Actions (`App\Actions\Proposals`, frozen §6 signatures)
```php
TransitionProposal::handle(Proposal $proposal, ProposalStatus $to, ProposalStatus $expectedFrom, array $input): TransitionResult
CorrectProposalStatus::handle(Proposal $proposal, ProposalStatus $to, ProposalStatus $expectedFrom, string $reason): TransitionResult
RecordFinalReportAcceptance::handle(Proposal $proposal, CarbonImmutable $acceptedOn): Proposal
```
- Transition and correction steps: `DB::transaction` → reload with `lockForUpdate()` → `Gate::authorize` on the locked row → stale check (`status` error = `proposals.stale_status`) → table check (`status` error = `proposals.transition_not_allowed`) → validation → status + `status_remind_on` (set entering on hold, else null) → one `ProposalStatusNote` → `ProposalStatusChanged::dispatch(...)`. The caller's `$proposal` is refreshed after commit.
- `ValidationException` error keys: `status`, `reason`, `effective_date` (Y-m-d, ≤ today), `remind_on` (Y-m-d, > today), and one key per unmet requirement (`linked_project`, `donor`, `planned_dates`, `budget`, `target_beneficiaries`, `final_report`).
- Note: `context` = the reason, or `proposals.status_moved_standard_note` when there is none; `date` = `effective_date` or today; `changed_by` = auth id; `is_correction` (true only from CorrectProposalStatus).
- `TransitionResult::$warnings`: T04 raises only `all_projects_archived` (entering CN review / proposal review while every linked project is archived).
- T07 hook: a comment in `TransitionProposal::handle` right after the save marks where `InviteDefaultReviewers` goes.
- `RecordFinalReportAcceptance`: `Gate::authorize('update')`; `accepted_on` error if the date is in the future; `final_report` error if no `final_report` media; saves quietly, then records the activity `proposal.final_report_accepted`.

### Policy abilities (`ProposalPolicy`)
`transition(User, Proposal, ProposalStatus $to)` → `proposals.update`; `correctStatus(User, Proposal)` → `proposals.correct-status`.

### Events
`ProposalStatusChanged($proposalId, $from, $to, $actorId, $isCorrection)` is dispatched once per move, inside the transaction. Its `ShouldDispatchAfterCommit` makes it fire **only after commit**. Tests prove none fires on a refusal or on an outer rollback.

## Deviations from contracts.md / the prompt
1. **`stage()` signature (Q1, Dev 1 to confirm):** §1 gives no type, and an enum case cannot see the pre-hold note. Built as `ProposalStatus::stage(?self $before = null): string` plus `Proposal::stage()`. No new enum. The developer approved this with the plan.
2. **`status` stays in `#[Fillable]` until slice 2 (Q3):** removing it now makes the legacy `fill(['status'])` callers throw under strict mode. The new writers already use direct assignment.
3. **Legacy allowlist in the guard (Q2)**, emptied in slice 2.
4. **`all_projects_archived` warning (Q5)** is emitted by T04; `reviewers_unseen` → T07, `no_agreement` → T08.
5. **`donor` and `planned_dates` cannot be tested as missing:** `proposals.donor_id`, `planned_date_begin` and `planned_date_end` are NOT NULL. The checks exist (the `donor` message reuses T03's `proposals.choose_the_donor`), but no test row can reach them.
6. **Pre-hold needs history:** a proposal put on hold whose trail has no earlier note has no pre-hold status, so it has no targets. Every real move writes a note, but legacy rows without notes would be stuck. The only way out is Correct Status, which is not available because on hold is not terminal. T27 rehearsal: check `on hold` rows without a prior note (none can exist before T04 ships).
7. Correcting into `on hold` clears `status_remind_on` (there is no reminder input on a correction).
8. TDD order: `CorrectProposalStatusTest` and `FinalReportCompletionTest` were written after the actions, not before them.
