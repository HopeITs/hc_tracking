**`SaveResult` `$validated`** (snake_case; the action validates it again):
`array{statement, type, checkout_period, program_id?, parent_id?, contributes_to_result_id?}`

- **Authorization:** `Gate::authorize('results.create' | 'results.update')`.
- **Locking and scope:**
  - With a `$proposal`, the proposal row is locked and the node lives in that proposal's framework.
  - Without one, the node lives in the program framework.
  - An existing node is reloaded through its framework, so another framework's node throws `ModelNotFoundException` (BOLA).
  - The parent is loaded in the same framework under `lockForUpdate`.
- **Rules:**
  - Levels follow `parentLevel()`. A parentless activity is refused. Nothing sits under an activity or a cross-cutting result.
  - An output with activities cannot change type.
  - `program_id`:
    - a child takes its parent's;
    - a proposal root takes `sharedProgramId()` (input ignored);
    - a program-framework root takes the input.
  - A changed program cascades to the subtree (query builder) unless `programChangeBreaksChain()` (moved here from the page).
  - `contributes_to_result_id`: proposal roots only, pointing to a `programFramework()` result whose `program_id` is one of `programIds()`.
  - Structural changes (create, parent change, type change) on a locked proposal need `results.update`.
  - An FK 1452 on save maps to `parent_gone`.

**`DeleteResult`:**

**`DeleteProposal`:**
- Steps:
  1. `Gate::authorize('delete', $proposal)` (`proposals.delete`).
  2. One transaction: lock the proposal row. Gone → return quietly (double click).
  3. Refuse with error `proposal`:
     - `proposals.this_proposal_has_a_funding_agreement_remove_the_agreement_f` when any agreement exists (guard kept);
     - `results_framework.proposal_delete_reported` when any target of an indicator in its framework has reports.
  4. Inside `Activity::withoutRecording`, delete the framework leaf-first through Eloquent, then `$proposal->delete()`:
     - indicators, their targets and `milestones.result_id` follow by FK;
     - `PlanIndicatorSourceObserver` removes the proposal's targets.
  5. Record exactly one `proposal.deleted` through `ActivityRecorder` (fan-out after commit).
- Needs only `proposals.delete`, not `results.delete`.
- `proposals/index` (`DeletesProposals::deleteProposal()`) calls it; a refusal shows the message as a danger toast.

### Observer (backstop): `ResultObserver::saving`

### `SaveActivitySchedule`
```php
final class App\Actions\Results\SaveActivitySchedule {
    /** @param array{months: list<'Y-m'>, weeks: array<'Y-m', list<int>>, expected_version: string} $input
     *  @return array<string, list<int>|null> the saved calendar */
    public function handle(Proposal $proposal, int $activityId, ?int $projectId, array $input): array
}
```
- Authorization runs before the transaction and again on the locked proposal row.
- One transaction:
  1. lock the proposal;
  2. load the activity through `Result::proposalFramework($id)->where('type', 'activity')` under a lock (another proposal's or a non-activity node → `ModelNotFoundException`);
  3. load the project through `$proposal->projects()` (an unlinked project → `ModelNotFoundException`).
- Rules:
  - stale `expected_version` → `schedule`: `schedule_stale`, nothing written;
  - continuous → every month from the first to the last given; event → the months given;
  - a month outside `scheduleWindow()` → `months`: `month_outside_period`;
  - a week outside 1–5 → `weeks`: `week_range`; weeks for a month not scheduled → `weeks`: `weeks_need_month`.
- Rows of that scope are replaced. An unchanged calendar writes nothing. An empty center calendar = back to the proposal calendar.
- Once the proposal is approved by the donor: one `result.updated` activity on the activity, `changes.schedule = [old summary, new summary]`, `properties.field = schedule`, `properties.project_id`. Nothing is logged before approval (plan Q4).

### `ShiftActivitySchedulesOnApproval`
- `App\Listeners\ShiftActivitySchedulesOnApproval implements ShouldQueue` (auto-discovered, `$tries = 3`) on `ProposalStatusChanged`.
- It does nothing unless `to = approved` and `actual_date_begin` is set.
- One transaction:
  1. lock the proposal;
  2. skip if `activity_schedule_shifts` has a row for it;
  3. delta = whole months from the month of `planned_date_begin` to the month of `actual_date_begin` (negative moves back);
  4. every schedule row of the proposal's activities (proposal calendar and overrides) is re-inserted at `month + delta`, weeks kept;
  5. insert the ledger row (`delta_months`, `shifted`).
- So a retry, a second event or a later re-approval after a correction does nothing. Months are not clipped to the actual end.

## Deviations from contracts.md / the prompt
1. **Branch:** `lifecycle-tasks-youssef`, not `lifecycle/T12-logframe` (the developer's standing rule; same as T11/T21/T23).
2. **The observer leaves legacy program-framework shapes alone** (plan Q1, approved).
   - The old 3-level order and program match are enforced by `SaveResult`, not the observer.
   - Why: `RealResultsSeeder` (Eloquent `firstOrCreate`) and `SeedIndicatorLibraryCommandTest` fixtures create output-under-output and impact-under-output rows across programs. The local DB holds 16 such rows. Enforcing these rules in the observer would break seeding and those tests.
   - Every rule a legacy row cannot already break (framework scope, activity, cross-cutting, cycle) is enforced in the observer.
3. **Lang key clash:** the prompt's `results_framework.contributes_to` (error message) already existed as the "Contributes to" label used by `framework-node` and the result modal. The label is renamed `contributes_to_label`, so the prompt key carries the message.
4. **New key `results_framework.parent_gone`** (plan Q5): the prompt asks for a "choose another parent" message but names no key.
5. **`DeleteResult` takes an optional `?Proposal`** (contract gives no signature) so the slice-2 tab can scope deletes (BOLA).
6. **New `App\Support\ProposalFramework`:** the lock and shared-program rules have one home for `SaveResult`, `DeleteResult` and the slice-2/3 tab and calendar.
7. **The structural lock for `on hold` / `rejected`** uses the pre-hold / pre-rejection status (plan Q2); a proposal with no notes counts as `concept note`.
8. **Tab host (slice 2, plan Q1):** a nested Livewire component inside T06's partial, not traits on `proposals/⚡show`.
9. **Proposal-level milestones** link only to their own proposal's activities (the prompt's test), which narrows §11.2's "or" list. "Funding" = linked through `project_proposal` at any status (slice 2 plan Q2).
10. **MEAL and Managers cannot open the tab in the app (Dev 1 to decide).**
    - They hold `results.*` but not `proposals.view` (§8), and `proposals.show` is gated by `proposals.view`.
    - The tab is built and tested as specified; the tests drive the component directly.
    - Until Dev 1 decides, `/results` (proposal filter and groups) is their working path to proposal frameworks.
    - Slice 3: the same applies to the calendar grid. MEAL edits it through the component, but cannot open `proposals.show`.
11. **New table `activity_schedule_shifts` (slice 3, plan Q2; Dev 1 to confirm).** §11.2 asks the shift to "run once" but names no record of it. A ledger table (like T31's `proposal_plan_shifts`) holds it. It is not a Phase 1 table.
12. **"MEAL" = `targets.update` (plan Q1).** After approval only MEAL edits the calendar; `results.update` cannot mean MEAL, since Managers hold it.
13. **Schedulable months follow the actual period once both actual dates are set (plan Q3).** The prompt names the planned period; after the approval shift the months sit in the actual period, so checking the planned one would lock MEAL out.
14. **`SaveActivitySchedule` signature** is chosen here (§11.2 names the action only). It takes a version fingerprint for the stale guard instead of an expected status.
15. **Schedule changes are logged on the activity** (`result.updated`, field `schedule`), only after approval (plan Q4). `ActivitySchedule` itself records no activity, so a cell toggle never logs a row per month.
16. **New lang keys** the prompt does not list: `weeks_need_month`, `schedule_stale`, `activity_kind_scheduled`, `choose_continuous_or_event`, and the grid's UI strings.
17. **«بلا رزنامة» badge on the grid rows only** (plan Q7), not on the tree nodes.
