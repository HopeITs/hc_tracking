### `App\Support\SupervisionMap` (contracts §10)
```php
final class SupervisionMap
{
    /** @return list<int> */
    public static function superviseesOf(int $supervisorEmployeeId): array;
    /** @param list<int> $superviseeEmployeeIds  @return array<int, list<int>> supervisee id => active supervisor employee ids */
    public static function supervisorsOf(array $superviseeEmployeeIds): array;
    public static function supervises(int $supervisorEmployeeId, int $superviseeEmployeeId): bool;

    // Helper, not in §10 (safe to use, not frozen):
    public static function flush(): void;   // forget this request's map after a write
}
```
- **Merges** the HR direct manager (`EmployeeProfile::managerOf()`, current position = active contract) with local `supervisions` rows. Returns **HR employee ids**, not user ids: map them with `app(EmployeeRecipients::class)->usersFor($ids)`.
- **Active only:** an employee inactive in HR (`employees.is_active`) has no effect on either side. Their local rows stay in the table.
- De-duplicated (HR + local same person counts once), sorted ascending, never includes the person themselves. `supervisorsOf()` returns a key for every requested id (`[]` when none).
- **Memoized per request/job:** the instance is `scoped` in `AppServiceProvider::register()`. Both actions call `flush()` after they commit.
- **Cost:** one query on `supervisions` + one HR query (`employees.id where is_active`), plus `EmployeeProfile`'s cached lookup (2 HR queries when cold). Same count for 1 or 10 ids. No `whereHas`, no HR write, no contract pay columns.
- **Supervision grants no permission and no visibility.** T17's "prepare on behalf" policy must still require `reports.create/update`.

### Table `supervisions` (migration `2026_10_14_121610_create_supervisions_table`)

### Writers and policy
- `App\Actions\Supervisions\AddSupervision::handle(int $supervisorEmployeeId, int $superviseeEmployeeId): Supervision`
  - `Gate::authorize('manage', Supervision::class)`.
  - Refusals (`ValidationException`, nothing written):
    - inactive / unknown employee → on `supervisorEmployeeId` or `superviseeEmployeeId`: `users.supervision_choose_an_active_employee`;
    - all others on `superviseeEmployeeId`: self `users.supervision_self`; supervisor already the HR manager `users.supervision_already_from_hr`; supervisee is the supervisor's HR manager or a local reverse row exists `users.supervision_mutual`; same local pair `users.supervision_duplicate`.
  - `DB::transaction`, pair read with `lockForUpdate`, Eloquent `create` with `created_by = Auth::id()`. A `UniqueConstraintViolationException` (two admins at once) is caught, re-read, and turned into the duplicate or mutual message, never a 500.
- `App\Actions\Supervisions\RemoveSupervision::handle(int $supervisionId): bool`
  - Gate as above; `DB::transaction` + `lockForUpdate()->find()`; Eloquent `delete()`.
  - Returns `false` when the row is already gone (no write, no activity): show `users.supervision_already_removed`.
- `App\Policies\SupervisionPolicy::manage(User $user): bool` → `$user->can('supervisions.manage')` (General Manager; Super Admin technically).

### Escalation (slice 2)
- `EscalationScanner`, manager stage (`escalate_manager_after_days` within `escalation_catch_up_days`, both from `NotificationSettings`): the active supervisors (`SupervisionMap::supervisorsOf()`) of the item's `directUserIds` also get a Critical `notifications.alerts.escalation.supervisor`, rule `escalation`, ledger stage `supervisor:{due}`.
- Skipped: the program managers alerted for that item (they keep only the manager alert) and the named people themselves. Items with no named people (role-watched: proposals, donor reports, transfers) get no supervisor stage.
- Tasks: a department-scoped supervisor (`TaskVisibilityScope`) only gets tasks they can open: one `TaskVisibilityScope::constrain()` query per department-scoped supervisor over all in-window task ids (same rule as `allows()`, batched). - Cost per scan: user→employee ids (1 query), the map (1 `supervisions` + 1 HR query), supervisor employee→user ids (1 query), the roles of task supervisors (1 + eager roles), plus 1 per department-scoped task supervisor. Nothing per item.
- New constructor dependency: `EmployeeRecipients` (container-resolved).
