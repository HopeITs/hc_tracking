#### `SaveProposal`
- **Authorization:** `Gate::forUser($actor)->authorize('create' | 'update')`. The sub-actions use `Gate::authorize` (the auth user), so `$actor` must be the logged-in user.
- **Create**, in one `DB::transaction`:
  1. Save the proposal. The status is the column default `concept note`; the action never writes `status`.
  2. Write the first note: `proposals.proposal_recorded_note`, `changed_by` = actor.
  3. Call `LinkProposalProject` for each project id, ascending.
  4. For a `proposal draft` start, call `TransitionProposal(→ proposal draft, reason = skipReason)`. That gives two notes. Any failure rolls everything back.
- **Edit:** locks the row and writes the details, the donor, the budget (money holders only) and the pivot `target_beneficiaries` of linked projects. It never touches links or status.
- **Not in the action:** the internal-number `UniqueConstraintViolationException` stays the page's job (narrowed catch around the call).

#### `LinkProposalProject`
- Locks the proposal, then `Gate::authorize('update')`.
- Loads the project through `Project::linkableToProposals()->lockForUpdate()`, then `Gate::authorize('view', $project)`.
- **Already linked:** no-op (no activity, pivot unchanged).
- **`closed` project:** calls `ReopenProjectAsDraft` first, in the same transaction.

#### `ReopenProjectAsDraft`
- Re-locks the project, then `Gate::authorize('reopenAsDraft')`.
- **Already `draft`:** returns. So the second of two concurrent linkers just links.
- **Any status but `closed`:** refused.
- **Open-project rule:** `openProjectFor(center, program, except self)` must return null.
- Then sets `draft` with `start_date`/`end_date` null, saved through the model. The history is in the `project.status_changed` activity.

#### `UnlinkProposalProject`
- Locks the proposal, then `Gate::authorize('update')`.
- Loads the project through `$locked->projects()->whereKey($id)->firstOrFail()`, so a project not on this proposal is a 404 (BOLA).
- Refuses the last linked project, and a project with reported targets of this proposal.

### Linkable-project rule
`App\Models\Project` `#[Scope] linkableToProposals()`:
- status ∈ {draft, approved, active, closed};
- no `ownerAssignment` with status `rejected`.

The actor also needs `projects.view`. Archived projects are never linkable.

**Pickers:**
- **Proposal page:** the scope minus already-linked projects. Empty without `update` on the proposal.
- **Project page:** empty unless the user `can('proposals.update')` and the project passes the scope.

### Policy
`ProjectPolicy::reopenAsDraft(User, Project)` = `proposals.update` and not owner-rejected. `ProjectPolicy::update` is unchanged.

### Money check (§8)
`SaveProposal::canSeeMoney($actor)` = `funding-agreements.view` || `transfers.view` || `accounts.view`. Without it, `requestedBudget` / `requestedCurrency` are neither validated nor written, and the stored values stay.

## Deviations from contracts.md / the prompt
1. **Planned dates stay required** (Q1, **Dev 1 to decide**).
   - The prompt says "nullable at creation", but `proposals.planned_date_begin/end` are NOT NULL (see T04 deviation 5).
   - Making them nullable is a schema change on a Phase 1 table that §7 does not list, so no migration was written.
2. **A `proposals.create` holder without `proposals.update` cannot create a proposal with projects.**
   - Why: `LinkProposalProject` authorizes `update`, and creating requires at least one project.
   - No built-in role has create without update (`config/access-control.php`).
   - The prompt's case (create-only + `proposal draft` → refused, nothing written) is tested and passes.
3. **MEAL recipients of `proposal.beneficiaries_changed` are exempt from `proposals.view`.**
   - Why: MEAL holds no `proposals.view`, so `RecipientFilter` would otherwise drop them.
   - Side effect: the notification links to a page they can't open.
   - §15.2 names "MEAL officer, MEAL Manager slot" as direct recipients, so **Dev 1 to confirm** this exemption, as for `donor_report.due`.
   - T21 adds the `EventCatalog` entry; T07 replaces `MealCoverage::mealManagerEmployeeId()` with `Slots::holderOf`.
4. **A closed project without a `center_id` is reopened without the open-project check** (Q5). It can't be checked without a center.
5. **"Visible to the user" = `projects.view`** (Q4). There is no row-level project visibility.
6. **Slice-1 page wiring:**
   - Link and unlink on both pages go through the actions.
   - The register's create/edit form (`ManagesProposalForm`) is **not** wired yet: it has no project picker, and `SaveProposal` requires ≥ 1 project. Slice 2 rebuilds it. It stays in T04's legacy status-writer allowlist until then.
7. **Project-page link permission:** attach/detach on the project page now need `proposals.update` (as the prompt says), not `projects.update`. Managers can no longer link from the project page.
8. **Source-scan guard widened:** `ActionAuthorizationTest`'s scan now accepts `Gate::forUser(...)->authorize(` as well as `Gate::authorize(`.
