## Delivered contracts (exactly as on the branch)

**Builder** `app/Support/ResultsChain.php` (final, read-only, no money read):
```php
ResultsChain::forProposal(Proposal $proposal, array $filters): array   // the proposal framework; milestones with proposal_id = P or on its linked projects
ResultsChain::forProgram(int $programId, array $filters): array        // program framework + the subtrees of proposal roots contributing to it
ResultsChain::forAnnualPlan(AnnualPlan $plan, array $filters): array   // program framework, this plan's targets only, activities with milestones planned in the plan year
// $filters: array{indicator: string, center: string, donor: string}  ('' = All)
```
Return shape (`@phpstan-type Chain` in the class):
- `tree`, `crossCutting`: lists of nodes `{result, depth, gaps, indicators, lineage, proposal, children, contributions}`.
  - `indicators[]`: `{indicator, code, name, linked, inactive, gaps, targets[]}`; `targets[]`: `{id, center, centerId, source, target, achieved, percent, status, issues}`.
  - `proposal`: `{name, url, donor, donorUrl}` on a proposal root shown on the program page; `url`/`donorUrl` are null without `proposals.view` / `donors.view`.
  - Activities only (slice 2): `milestoneGroups[]` = `{centerId, center, progress, hasCancelled, milestones[]}`, `milestones[]` = `{milestone, issues, cancelled}`; `schedule` = `array<'Y-m', list<int>|null>` (proposal calendar; under a center filter, that center's override when it has one). Other levels get `[]` for both.
- `unlinkedMilestones` (milestones of the scope with no `result_id`), `options` (`indicators` = library entry ids, `centers` = project ids, `donors` = donor ids), `filters` (the resolved values), `summary` (`levels`, `indicators`, `unmeasured`, own framework only), `gaps` (counts), `isEmpty`.
- Gap keys: `no_indicators`, `no_target`, `no_milestone`, `unlinked_milestone`.
- Achievement: `PlanIndicator::achievedValue()` / `percentAchieved()` / `achievementStatus()` only. Each target is its own row; nothing is summed across centers or donors. Chain issues come from `PlanIndicator::chainIssues()`.
- Target sources (proposal / annual plan) are resolved with two `select`ed reads, never `morphTo` (which would select `proposals.requested_budget`).

**Milestone statics (slice 2; not in contracts.md, Dev 1 please review):**

```php
Milestone::activityLinkIssuesFor(iterable $milestones): array<int, list<string>>  // batch twin of activityLinkIssues(), 3 queries total, same keys
Milestone::weightedProgress(iterable $milestones): ?float                         // reached ÷ non-cancelled weight ×100, 1 dp, null when no weight counts
```
`weightedProgress()` is the PHP form of the `withSum` reads in `ReadsProjectDelivery::milestoneProgressPercent()`, `ReadsProgramDelivery::milestoneProgress()` and `projects/⚡index`. Those pages were not changed.

## Deviations from contracts.md / the prompt
1. **Branch:** `lifecycle-tasks-youssef`, not `lifecycle/T16-chain-view` (the developer's standing rule, as in T11–T13).
2. **Proposal tab placement (plan Q1, developer):** a Structure / Chain toggle. Structure (the editable T12 tree) stays the default, so `ProposalLogframeTest` is unchanged.
3. **Program contributions (Q2):** shown as a folded "N proposals contribute" list under the program result, each with its read-only subtree. Only roots whose `contributes_to_result_id` is a result of *this* program are shown, so a multi-program proposal appears under each program its roots point to.
4. **Annual plan scope (Q3):** impact/outcome/output/cross-cutting of the program framework, with this plan's targets only; activities only when a linked milestone is planned in the plan year (dates overlap the year).
5. **"Milestone without activity" scope (Q4):**
   - proposal: its milestones + its centers' milestones;
   - program: its projects' milestones;
   - annual plan: the program's milestones planned that year.
   - They are listed under the tree.
6. **Filter values:** indicator = library entry id (unlinked legacy indicators are not options). The donor picker shows only with ≥ 2 donors in scope. The center filter also matches an activity through its milestones' project.
7. **Program page layout:** the old horizontal branch cards are replaced by the vertical indented tree (same mark/accent identity), so long indicator lists and the per-center breakdown fit at 375 px and in print.
8. **"Start Logical Framework":** the proposal tab opens the T12 create modal; the program and annual plan pages link to `results.index`. No route was added.
9. **Slice 2 partial (developer decision, 2026-10-16):** T31 is not on the branch (`tasks.department_id/kind` missing, `milestones.project_id` still NOT NULL), and neither is T17 (no `project_activity_statuses`). So the department-tasks summary and the D-51 status badge are not built, and milestones are grouped by project only (a proposal-wide milestone cannot exist yet).
10. **Center filter (slice 2):** an activity that has only a center-specific calendar row, and no target or milestone in that center, is still hidden by the slice 1 filter rule. The rule was not widened.
