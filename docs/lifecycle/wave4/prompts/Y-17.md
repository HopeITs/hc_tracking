## Goal
Until now `projects` was written first and mirrored to the row (Y-11). This task turns it around: the **row is the only thing written**. Approving a proposal completes its rows and creates no project; activating, closing, archiving, restoring, the owner's acknowledgement, files and sectors act on the row; a proposal no longer "links" projects. After this task no code path creates or updates a `projects` row, and Y-18 can drop it.

- **Slice 1:** the row's lifecycle actions replace the project's; events. **[contract]**
- **Slice 2:** the proposal path: approve, materialise, save, extend, renew, transition. **[contract]**
- **Slice 3:** the mirror, the link actions and the open-project rule are removed; the status guard moves.

## [contract] (D-92, D-93)
Replace `contracts.md §3` with a section of the same number, **"Location statuses and transitions"**:

> A location row has a `status` (`ProjectStatus` values: `draft`, `approved`, `active`, `closed`, `archived`). The transition table and its guards are those of the former project table, with the row in place of the project and these actions as the **only** writers of `proposal_locations.status` (`LocationStatusWriteGuardTest`):
> - `ApproveLocationFromProposal::handle(ProposalLocation $row, string $via): bool` (`$via` ∈ `proposal_approval`, `owner_acknowledgement`; idempotent): `draft` → `approved` once the proposal is approved **and** the row's responsible has acknowledged; sets the row's dates from the proposal.
> - `ActivateLocation::handle(ProposalLocation $row, string $via): void` (`$via` ∈ `template_confirmation`): `approved` and dated → `active`; when every row of the proposal that is not archived is active, moves the proposal `approved` → `active`.
> - `CloseLocation`, `ArchiveLocation`, `RestoreLocation`, `ReopenLocationAsDraft`: as their project twins.
> - `SaveLocationDetails::handle(ProposalLocation $row, array $data, User $actor): ProposalLocation`: description, calendar, the five targets, sectors. City, program, centers and responsible are changed only through `SaveProposal` (before approval) or a change request (Y-09).
> - `SaveLocationFile`, `DeleteLocationFile`: as their project twins.
>
> **The open-project rule (L94) is withdrawn.** Two proposals may each have a row at the same city, program and center; whether they share a monthly report is MEAL's choice (D-77). `openProjectFor` is removed.

In `§5`: `LocationActivated(ProposalLocation $row)` and `LocationPeriodChanged(ProposalLocation $row, …)` replace `ProjectActivated` and `ProjectPeriodChanged`; the notification keys `project.activated` and `project.period_changed` keep their names.

In `§6`: `MaterialiseProposalLocations::handle(Proposal $proposal, int $actorId): MaterialisationResult` no longer creates or links a project: for each complete row it calls `ApproveLocationFromProposal($row, 'proposal_approval')` and reports rows approved, rows waiting for their owner, rows waiting for their program. `LinkProposalProject`, `UnlinkProposalProject`, `ReopenProjectAsDraft`, `SaveProject`, `CloseProject`, `RestoreProject`, `ApproveProjectFromProposal`, `ActivateProject` are **removed**. `SaveProposal` no longer accepts `projectIds`. `ApproveProposal` requires at least one row (`locations_complete` already demands every row be complete); the `linked_project` requirement is removed.

In `§12.4`: `ConfirmReportTemplate` calls `ActivateLocation` for each row of the template's proposals at its place.

In `§8`: the `projects.create` row is removed (nothing creates a project by hand); `projects.update` and `projects.delete` gate the row's details and its archive.

## Rules
- **Slice 1.** Each new action is its project twin moved, not rewritten: same guards, same locks (lock the row, then its proposal, always in that order), same activity events with the row as subject. Until slice 3 the old project actions stay and delegate to the new ones so nothing breaks mid-task.
- `target_beneficiaries` lives on the row (Y-11). `SaveProposal::beneficiaryChanges()` and the `target_beneficiaries` requirement in `TransitionProposal` read and write the row, not the `project_proposal` pivot; the activity `proposal.beneficiaries_changed` keeps its payload shape with `location_id` in place of `project_id`.
- The page's write buttons (Y-16 slice 2 left them on project actions) call the row actions.
- `MediaOwnerObserver`: observes `ProposalLocation`; deleting a row deletes its media. A row with milestones, risks, targets with reports, or a template cannot be deleted: `ProposalLocationRows::replace()` refuses to remove it before approval too (`proposals.location_in_use`).
- **Slice 2.** `ApproveProposal`: `lockLinkedProjects` becomes "lock the proposal's rows ordered by id"; `outcomeFor()` reports per row (funded, waiting, extended, skipped) with the same keys. The approve preview (Y-01) says "N places approved, K waiting" and no longer "will create N projects".
- `ExtendProposal::widenProjects` becomes `widenLocations`: sets each dated row's `end_date` to the new end; never shortens. `ProjectPeriods::widen` is replaced by `LocationPeriods::widen`.
- `CloneProposalForRenewal`: copies the previous proposal's **rows** (city, program, responsible, centers or field work) whose HR center is still active; no project is looked up, reopened or replaced. Milestones follow their row's twin (Y-12). The renewal rule of `projects.md` (D-30) is rewritten with `record-rule`: "a renewal is a new proposal with its own rows".
- `TransitionProposal`: auto-archive when all the proposal's rows are archived. `InviteDefaultReviewers`: the rows' responsibles and programs.
- `GenerateMonthlyReportsForProject` listens to `LocationActivated`; after Y-03 it already generates per template. Rename it `GenerateMonthlyReportsForLocation`.
- The commands `MapProjectCenters`, `BackfillProposalLocations`, and `ProposalLocationBackfill` are one-off tools of earlier tasks: delete them. `PrepareMonthlyReports`, `BackfillMonthlyReports`, `PrefillActiveReportTemplates` read active rows / templates.
- **Slice 3.** Delete `ProjectLocationMirror` and every call to it, `ProposalLocationRows::attachProject` / `detachProject`, the branches on `row->project_id` in `incompleteRowIds`, `replace`, `update`, `syncRequest` (a row is complete with program, responsible and a center, field work or `is_new`; "stands for a project" is gone), `locations:verify-mirror`, the ten project actions, `ProjectPeriods`, `Project::openProjectFor` and its callers.
- `ProjectStatusWriteGuardTest` becomes `LocationStatusWriteGuardTest`: it scans for writers of `proposal_locations.status` and allows only the actions listed in the `[contract]`. A second assertion: **no file under `app/` writes the `projects` table** (no `Project::create`, `->save()` on a `Project`, `DB::table('projects')` write, or `projects()->attach/detach/sync`).
- `proposal_locations.project_id` is no longer written for new rows. Existing values stay until Y-18. Every other legacy `project_id` (milestones, risks, targets, schedules, statuses, plan updates, templates, reports) is written as **null** for records created on a row without a project: check each column is nullable and say so in the handoff.
