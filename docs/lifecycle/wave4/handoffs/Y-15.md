**Model `App\Models\ActivitySchedule`**

```php
#[Fillable(['result_id', 'project_id', 'proposal_location_id', 'month', 'weeks'])]
public function location(): BelongsTo                                              // belongsTo(ProposalLocation::class, 'proposal_location_id')
public function project(): BelongsTo                                               // kept until Y-18
public static function effectiveFor(int $activityId, ?int $locationId): array      // one query, then effectiveOf()
public static function effectiveOf(Collection $rows, ?int $locationId): array      // the rule itself, on rows already loaded
// casts: 'proposal_location_id' => 'integer'
```

`effectiveOf($rows, $locationId)` works on one activity's rows. If the location has rows of its own, they are its calendar; otherwise the rows with no location are; a null `$locationId` gives the proposal calendar. Rows of other locations are ignored. `effectiveFor()` calls it, so the rule exists once. Every reader that renders many activities loads the rows once and calls `effectiveOf()`.

```php
public function handle(Proposal $proposal, int $activityId, ?int $locationId, array $input): array
```

- The post-approval log `result.updated` now carries `proposal_location_id` as well as `project_id` in its properties.

**Writers**

- `ShiftActivitySchedulesOnApproval`: copies `proposal_location_id` and `project_id`.

**Readers, all through `effectiveOf()`**

| Reader | Which row it reads |
| --- | --- |
| `⚡activity-calendar` (proposal Logical Framework tab) | The scope picker lists the proposal's rows (`ProposalLocation::label()`). `scopeLocationId` replaces `scopeProjectId`. The overrides are loaded once. |
| `BuildsProjectGantt::planActivities()` | The row of *that* proposal carrying the page's project: one `proposal_locations` query per proposal. |
| `ReportTemplateReader::calendarFor()` | Each template proposal's row at the template's city and program. The `PlaceBridge::legacyProjectIdFor()` read is gone. |
| `MonthlyReportActivities::for()` (schedule part only) | The same, via the report's template. |
| `ResultsChain::scheduleOf()` | The centre filter (a project id) maps to the row of the result's proposal carrying that project. One query per page, only under a centre filter. |

**New helper `App\Models\ReportTemplate::locationIdsByProposal(array $proposalIds): array`.** Given `list<int>`, it returns `array<proposal id, row id>`: each proposal's row at the template's city and program, lowest id when a proposal has two. It is one query, shared by the template reader and the monthly report. Slice 2 should use it for the statuses.

**Backfill**
- `App\Support\Locations\ScheduleOverrideRowBackfill::run(bool $apply): array{overrides_seen, moved, by_own_proposal, by_date, by_most_recent, rows, unmapped}`.
- It maps through `ProjectSuccessor::rowsFor($projectId)`, filtered to the activity's `proposal_id`. Zero candidates, or more than one, means the override is listed and left.
- `by_date` and `by_most_recent` are always 0, because no date rule applies.
- Command: `activity-schedules:row-backfill {--dry-run}`. Lang keys are under `results_framework.console.*` (en and ar).

**Factory.** `ActivityScheduleFactory::forLocation(ProposalLocation $row)` sets both keys.
