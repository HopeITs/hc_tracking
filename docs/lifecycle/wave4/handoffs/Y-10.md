## Deviations from contracts.md / the prompt
These were agreed with the developer at plan (17 Nov) and **need Dev 1 ratification**. They are in `contracts.md §12.1` as a quoted paragraph.
1. **Q2: a row that has targets is not removed.** `ProposalLocationRows::replace()` (a row dropped from the form) and `detachProject()` (unlink) refuse on `locations` with `proposals.location_has_targets`. Without this, the restrict FK raises a raw SQL error. Targets are never deleted silently.
2. **Q3: deleting a proposal.** `PlanIndicatorSourceObserver` now deletes a proposal's targets on `deleting`, before the database cascade from `proposals` to `proposal_locations` meets the restrict FK. `DeleteProposal` already runs in a transaction. Annual plans still clean up on `deleted`.
3. **Q4: beneficiaries stay on `project_proposal`.** The grid's default `target_population` and `PlaceBridge::targetBeneficiariesOf()` read `project_proposal.target_beneficiaries` through the row's `project_id`. The row has no beneficiaries column yet. The PHPDoc now says "removed by Y-11" (it was "by Y-10").
4. **Q5: chain check by id.** For a row target the only chain rule left is "an indicator tied to a project takes targets only on the row carrying that project". It compares `indicators.project_id` with `proposal_locations.project_id`, so no `Project` is loaded.
5. **Q6: `syncPlaceFromRow()` also writes `project_id`.** When the approval links a project to a row (`attachProject`), the row's targets get it, so `forProjectInWindow` and the other legacy readers keep finding them.
6. **Q7: the backfill re-places linked targets from their row.** That way a project-centred target on a multi-center row becomes shared (D-90). It does **not** change `project_id`.
7. **Factory:** `PlanIndicatorFactory` links a proposal target to the proposal's row carrying its `project_id` (or the `proposal_location_id` the caller gives) and copies that row's place. It never creates a row. The plan said "or create one"; dropped, because creating rows would change many unrelated fixtures.
8. **Grid between slices (Q1):** slice 1 re-keyed the component so the tab keeps working. Slice 2 still owns the header (center chips, "Field work", "Center not set", the shared sentence, the disabled waiting row). The panel title still reads "Targets per center" and the "Targets outside the grid" subtitle still says "a project it no longer links": both are for slice 2's wording pass.

## Callers of `syncPlaceFromRow()`
All are inside `App\Support\ProposalLocationRows`, so they run in the caller's transaction:
- `update()` (via `replace()`): the row's centers or `city_wide` changed. This covers `SaveProposal` and the Y-09 approved change (`SaveProposal::applyChange`).
- `fillEmpty()`: the Y-01 post-approval center fill, both branches.
- `attachProject()`: a second project on the same city and program adds a center (the target turns shared), and a waiting row gains its project. This covers approval materialise through `LinkProposalProject`.
- **Template lines are not touched.** A target that turns from single-center to shared keeps its existing `report_template_lines` (one template). A prefill re-run (`report-templates:prefill-active`) or Y-04 must add the line in the new center's template.
