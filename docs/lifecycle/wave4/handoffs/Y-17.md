**Two simplifications the row makes possible**, because a row belongs to exactly one proposal (D-93):

- Approval takes **its own** proposal's grant window, so the "earliest begin / latest end across proposals" merge of `ApproveProjectFromProposal` collapses to one pair. Nothing shortens (`LocationPeriods::widen`).
- `ActivateLocation` moves the **proposal** `approved → active` once every row of it that is not archived is active — an archived row holds nothing back.
- `RestoreLocation` and `ReopenLocationAsDraft` drop the open-project check entirely.

## What changed around the edges

- **`ProposalLocation`** now returns `['responsible_employee_id']` from `assignmentFields()` — as the model's own docblock had promised Y-17 would — so the row asks its responsible to acknowledge, and `assignmentAcknowledged()` approves the row. It implements `TracksActivity` and answers `recordActivity()` **without** turning on `RecordsActivity`'s created/updated/deleted fan-out: `SaveProposal` still records the set's change once, with counts.
- **`project.created` is now the row's event.** `ProposalLocationObserver::created()` records it. This matters: it is the notification whose quick action the responsible answers with acknowledge or reject (`QuickActions`), and nothing creates a project by hand any more to record it. Without it a waiting row had no notification to carry the action.
- **`Project`** asks nobody to acknowledge anything (`assignmentFields()` returns `[]`) and mirrors nothing.
- **The project page and form.** Close, archive, restore, the files tab, the appointment and the nudge call the row actions. The edit form became the row's **delivery** form — description, the five targets, sectors — and no longer creates, names, places or dates a place. The create path was already unreachable from the UI (Y-16 deviation 12).
- **The proposal page** lost its link form and unlink button; the project page's funding panel lost its link and unlink controls. "New Concept Note" now names a **place**, and seeds the new proposal's first row from it.
- **The approve preview** says "N places approved, K waiting for their responsible, M waiting for a program" instead of "will create N projects".

### The Quality bar's query budget, and what measuring it found

`ProposalApprovalTest` → "an approval with six places costs no more queries per place than one with two" asserts the slope (`$six - $two <= 4 * 70`) and the base (`$two <= 200`).

Measuring it found a real redundancy: **`ApproveProposal` ran every row through `ApproveLocationFromProposal` twice** — once inside `MaterialiseProposalLocations::handle()` and once in its own `approveRows()`. The outcome was correct (the action is idempotent, and the result lists were built from the pre-approval states), but each place paid for two locks of its row and of the proposal. `approveRows()` is now `outcomesOf()`: it reads the states before anything moves and writes nothing, and materialising is the one pass over the rows.

The remaining cost per place is ~61 queries, and it is the **activity fan-out** — each place records one `project.approved` and notifies its own people, exactly as each project did before Y-17 — plus Spatie permission re-reads inside the loop. Neither is something Y-17 introduced. The budget is a regression guard on the slope, and the test says so rather than implying the slope is small.

### The reader Y-16 missed that Y-17 would have broken

`BuildsPortfolioGantt::agreementGanttPayload()` built the agreement chart's delivery rows from `$proposal->projects()`, and handed each **project** to `pushProjectBranch()`, which has taken a `ProposalLocation` since Y-16. Y-16's grep could not see it, because it reaches the pivot through the relation rather than naming `Project`. Left alone it would have shown **no delivery rows at all** for every proposal created from Y-17 on. It now reads the proposal's own rows with the same eager loads `timelineProjects()` uses.

`tests/Feature/AgreementGanttDeliveryTest.php` is new and covers it: one delivery row per place with no project anywhere, the place's own period and status on the chart, an agreement whose proposal has no place showing the grant alone, another proposal's places never reaching this chart, and no amount in the payload for a viewer without money access. A Gantt row is named by its proposal (`headline()`, Y-16's rule for the shared branch), which is why every place of one agreement shares a name.

### The link gate in the proposal form, and the guard that replaced it

The form refused to remove a location row "because it stands for a linked project", and locked its city and program for the same reason — while `ProposalLocationRows::replace()` had stopped protecting such rows in slice 3. The two disagreed, so the link gate went: the `'project'` key is off the form's row payload, `proposals.location_linked_project` is no longer rendered, and `proposalPlaceRow()` in `tests/Pest.php` dropped it too.

Removing it left the row **unguarded**, which the full suite caught (`ProposalLocationRowsFormTest` → "an approved proposal row takes centers"). The link only ever existed after approval, so what it really protected was a place already being delivered at. **The row's own state replaces it**: a row whose status is past `Draft` is locked — its city and program cannot be changed and no Remove button is drawn — and `removeLocationRow()` refuses it server-side too, not just in the view, which the old gate never did. `loadLocationRows()` carries a `locked` flag for it. Beyond that, `refuseWhenRowInUse()` still refuses on save, with `proposals.location_in_use`, a row carrying targets, risks, a schedule or a report template.

The locked reason names the state instead of the withdrawn link: `proposals.location_linked_place_locked` ("The linked project sets this. Unlink it in the Projects tab to change it.") became **`proposals.location_approved_place_locked`** ("This place has been approved, so it cannot be moved. Archive it instead."), in both languages.
