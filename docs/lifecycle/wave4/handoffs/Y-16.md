1. **The bell lost Acknowledge and Reject** on an owner-assignment notification. Y-16 moved the subject to the place; the assignment is still filed on the project until Y-18, so `QuickActions` was asking the row for a record that was never written there. `ProposalLocation::currentOwnerAssignment()` answers with the row's own assignment, or the project's when the row holds none, and a project with no row yet answers for itself.
2. **"Mark as seen" never fired**, for the same reason: `mount()` read `$row->currentAssignment('responsible_employee_id')`.
3. **The unblock dialog 404ed** on a blocked place, and when it did open it lifted the block on the row while leaving the project blocked — the two screens then disagreed. It now lifts it where it was raised and lets `ProjectLocationMirror` carry it to the rows.
4. **The proposal's grant paperwork vanished.** `projectFiles()` queried `mediable_type = 'project'` while handing it the ids of **places**, so a funded place's papers never appeared and the download link resolved the wrong record. The preview route refused a place's paper with a 404 for the same reason.
5. **Moving a task offered `project:ID` for rows it had listed as places**, and compared the current one against the same wrong spelling — the dialog never marked where the task already was, and a move sent an id `MoveTask` reads as a project's.
6. **The results chain threw on the programme page**: it selected a row without `city_wide`, `city`, `programme` or `centres` and then asked it for `label()`. A scoped instance's chip also named a project rather than its place.

A seventh was found by the renewal suite and is a reading, not a slip: **a place's funding history had become a single grant.** A place is of exactly one proposal (D-93), and `fundingHistory()` took that literally, so the project page listed one year where it used to list every year of the work. A grant renewed for a third year is the same work at the same place, and this page is where that is read, so the renewal chain the place's proposal sits in is now walked both ways.

Two further defects were **red on `main` as well** and are fixed here because they stood in the way: `$target->project` lazy-loading on the annual plan's summary and on the chain's targets (D-44 keeps the project as the right name there, so both now eager-load it).

One performance defect: the report-template queue resolved each line's place in its own query, which the page's fixed-query guard caught the moment a second template existed. `ProjectSuccessor::rowForMany()` answers for the whole queue in one.

### Slice 4 · the Desk, the calendar, the programs, the money

- **`ProjectStage` takes a `ProposalLocation`.** Its lead is the row's one proposal (`leadOf()`, D-93), `locationIdsAt()` replaces `projectIdsAt()`, and `signals()` reads the monthly reports at the row's place and the proposal's transfers.

## New test helpers (`tests/Pest.php`)

- `rowFor(Project $project, ?Proposal $proposal = null): ProposalLocation` — idempotent; the row carries the project's status, dates, beneficiaries, description and calendar, and its proposal takes the project's own name (the project id is appended only when another proposal already holds that name, so a register that names the proposal reads as the fixture wrote it).
- `projectWithRow(array $attributes = []): Project` — the common case with no factory state.
- `reportAtRow(ProposalLocation $row, array $attributes = []): MonthlyReport` — a monthly report at the row's place, with the template the row needs; `ReportTemplateFactory` carries a legacy template with a row of its own (Y-03), and that second row is removed here since it would sit at the same place and read the same report.

These three are why the fixture conversion was tractable at all: the earlier attempt put an automatic row on `ProjectFactory` and it rippled into MEAL coverage, template prefill and the proposals register.
