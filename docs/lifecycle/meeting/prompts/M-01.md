## Rules
**Slice 1**
- Base: the library entry dialog (form B) with its fields and its generated code, kept as it is. Every entry point that today opens the old indicator dialog (indicators page "Add", quick-form on results and the logframe, targets "attach") opens this dialog or the picker instead. No second layout of the same fields.
- Who: the MEAL team and the CEO. Permissions do not change: `config/access-control.php` already limits `indicators.create` and `indicator-library.create` to the person in the MEAL Manager slot (`meal_manager_only`), with `Super Admin` and `General Manager` (the CEO, who holds every permission) bypassing it. Creating or editing a library entry keeps those checks. A user without them sees the picker only (choose an existing indicator, never create one). Record in the plan which roles can add an indicator before and after (expected: the same) and stop if any role loses it.
- Name: Arabic required, English optional (already so). Above the name fields, a searchable "existing indicators" picker over `LibraryIndicator` names (both languages searched). Choosing an entry opens it instead of creating; typing a name that already exists shows the match and offers to use it. Server-side duplicate check in `SaveLibraryIndicator` too (case- and whitespace-insensitive, `name_ar` and `name_en`), never only the UI.
- From a logframe row: saving or picking an entry then attaches it to that result with `AttachLibraryIndicatorToResult` (project, baseline and target are entered in the logframe table, slice 2, not in this dialog). Record in the plan how `Indicator.name` (single column) is filled from the entry; add no column without a migration that follows `database-migrations.md`. Show the name in the user's language with the other as fallback.
- Fewer fields on first sight: keep form B's sections, but collapse the advanced ones (numerator/denominator, calculation method, disaggregation, collection frequency note) under "More options"; name, placement, measure, unit and frequency stay visible. Plain words, EN and AR, one term per idea (`review-page` §3).

**Slice 2**
- One table component rendering a proposal's framework rows: level, description, indicator, baseline, target, means of verification, assumptions/risks. Fixed column names, horizontal scroll, sticky first column and header. Row actions: add row below, add indicator (opens the slice-1 form), edit, remove.
- Standalone MEAL page in the sidebar (route + `->can(...)`, reuse the results/logframe permission), proposal picker on top, same table. The proposal's Logical Framework tab renders the same component (read-only where the user cannot edit). Retire the old Results page by redirecting its route to the new page; do not delete other pages (M-04 does).
- Page inside `x-desk.register` per `pages.md`; at most one search and one picker visible; the rest behind "More filters".
- Do not load per row: eager load once, assert the query count in a test.
